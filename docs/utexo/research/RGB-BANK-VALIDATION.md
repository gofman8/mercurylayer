# Вердикт по концепции «RGB-банк» (для валидации Адамом)

Проверено по исходникам именно той линии консенсуса, на которой стоит наш стек: rgb-consensus 0.11.1-rc.10 / rgb-aluvm 0.11.1-rc.3 / rgb-schemas 0.11.1-rc.10 (форк rgb-protocol, запинен в `/Users/gofman/Claude/utexo-rgb-lib/Cargo.toml:95-98`), плюс релизная линия RGB v0.12 (ultrasonic/zk-aluvm), RFC RGB-WG #7 и LNP-BP discussion #125. Каждое утверждение прогонялось через адверсариальную перепроверку.

---

## 1. Вердикт

Ядро модели работоспособно, но заявление «двух софтфорков достаточно» неверно как утверждение о достаточности. Что реально: (a) замок «банк не может украсть» строится уже сегодня, без изменений консенсуса — через кастомную схему на существующих опкодах `ldp` + `vts` (подпись владельца над transition id), с прецедентом PFA; (b) батчинг всех клиентов на одном UTXO нативен (до 65 535 транзитов в одном бандле, по одному подписанному транзиту на владельца); (c) оба «софтфорка» Бориса — это изменения консенсуса RGB (все валидаторы обновляются), а не Bitcoin, причём fallback-сил — это принятый RFC #7 (авторства adambor), а не фантазия. Что ломается: несущая дыра — burn с тотальным сокрытием данных — это проблема доступности данных (DA), которую не закрывает никакое изменение RGB-консенсуса: клиентская валидация не имеет глобального состояния, on-chain-якорь — невскрываемый хеш, а fallback-по-burn сам по себе неадъюдицируем без сокрытого раскрытия бандла. Важная поправка аудита: точечный burn «честным» пропуском Opout доказуем жертвой при наличии любого со-получателя того же батча (input_map полный в каждом консайменте), но банк может заранее «застаффить» input_map фиктивным OpId — и тогда burn снова неотличим от «перевод сделан, данные не выданы». Итоговый счёт: замок владельца (уже есть) + fallback-силы (изменение консенсуса на живом форке 0.11) + гарантированная публикация раскрытия каждого батча (внешнее допущение — публикационный слой). Модель с добавленным DA-слоем изоморфна Todd-2017 — то есть тому, что у нас уже реализовано в pop-ledger. Отдельно: нативный RGB-HTLC невозможен (нет таймаута в VM ни в 0.11, ни в 0.12), заморозка/шантаж на выходе не закрыты ни одним из обсуждённых ингредиентов — без выхода в одностороннем порядке дизайн ниже нашей планки «freeze ≠ seize» ([TRUST-MODEL.md](../TRUST-MODEL.md) §3, T-SE-2).

## 2. Проверка утверждений из переписки

| Утверждение из чата | Статус | Что на самом деле |
|---|---|---|
| «Контракт требует подпись владельца на любой транзит его аллокации» (нужны новые фичи RGB) | **Подтверждено, фичи уже есть** | `Transition.signature: Option<Signature>` (rgb-consensus src/operation/operations.rs:363), опкод `Vts` — ECDSA над transition id (src/vm/op_contract.rs:490-514), OpId подпись не включает (commit.rs:311-322, нет цикличности). Прецедент: схема PFA «issuer must co-sign» (rgb-schemas src/pfa.rs:52-69, помечена «not production-safe»). Оговорки: (1) один слот подписи на транзит → каждому владельцу свой транзит в бандле (нативно: `TransitionBundle.input_map: NonEmptyOrdMap<Opout, OpId, U16MAX>`, bundle.rs:137-139); (2) ECDSA, не BIP340 — наш MuSig2-энклав не подпишет без нового пути; (3) builder-API отсутствует (rgb-ops builder.rs:443 жёстко ставит `signature: none!()`); (4) схема фиксируется в генезисе — существующие NIA/CFA/IFA активы не ретрофитятся. |
| «Банк не может украсть, только сжечь/заморозить» | **Частично** | Верно ТОЛЬКО для бесподной схемы «pubkey в owned state каждой аллокации + `ldp`+`vts`» — её ещё нет, надо писать. С отгруженной PFA (единый глобальный ключ) банк, держащий этот ключ, крадёт легально. Плюс: PFA-паттерн = перманентный SPOF — ключ в генезисе неротируем, его потеря = вечная заморозка всех, а liveness подписанта гейтит любое движение состояния. «Только burn/freeze» — верно при правильной схеме; сам burn/freeze ничем в 0.11 не ограничен. |
| «В RGB есть хеш-лок, но нет таймлока» | **Частично** | Хеш-проверка выразима в скрипте валидации (DigestOp sha256/blake3 безусловно в ISA, rgb-aluvm instr.rs:78-80; exec.rs:1386-1450), но ни одна отгруженная схема её не пакует. Таймлока нет совсем: полный набор опкодов (op_contract.rs:44-187) не читает высоту/время/поля witness-tx; WitnessPos{height,timestamp} есть в валидаторе, но недостижим из скриптов (только для упорядочивания операций, RCP-240731A). Важно: в 0.12 digest-опкоды УДАЛЕНЫ (zk-aluvm — чистая арифметика поля) — хеш-лок-схема 0.11 не портируется. |
| «opret: проверить отсутствие OP_RETURN; tapret: доказательство отсутствия коммита в taptree» | **Частично** | Метод выводится из первого DBC-пригодного выхода tx (validator.rs:464-484), поэтому opret-проверка = «нет ни OP_RETURN, ни P2TR». Tapret partner-proof (dbc/tapret/mod.rs:168-227) — не самостоятельное доказательство отсутствия: это райдер уникальности внутри доказательства присутствия, требует `internal_pk`, который есть только у автора tx (mod.rs:427-429). Но: банк-автор МОЖЕТ доказывать отсутствие (раскрыть internal_pk+taptree; для opret — MerkleBlock с entropy, mpc/block.rs:185-188) и может структурой tx принудить opret (OP_RETURN раньше любого P2TR) — тогда коммит публичен. Протокол банка может сделать это обязательным. |
| «Малициозный банк жжёт и не публикует консаймент — доказать burn невозможно» | **Частично (главная поправка аудита)** | Три класса: (1) Точечный burn честным пропуском — ДОКАЗУЕМ без кооперации банка: input_map ключуется по Opout, никогда не скрывается (bundle.rs:235-250), полный в консайменте каждого со-получателя, BundleId коммитит только его (bundle.rs:142-146), один бандл на контракт на witness (MPC-слот детерминирован, block.rs:248-265) → «мой Opout ∉ input_map» проверит третья сторона. (2) НО банк может застаффить input_map фиктивным OpId для Opout жертвы — валидация это пропускает (validator.rs проверяет только known_transitions ⊆ input_map) → снова неотличимо от «перевод скрыт». (3) Тотальный burn с невыдачей консайментов никому — недоказуем ни в какой конечный момент (поздние данные валидны). Вырожденные формы tx (нет ни OP_RETURN, ни P2TR → NoDbcOutput; кривой первый OP_RETURN) — публично доказуемый тотальный burn, но злоумышленник их просто избегает. Итог: у банка всегда остаётся недоказуемая стратегия burn; закрывается только внешним публикационным слоем. |
| «Автоперенос неподписанных аллокаций на следующий UTXO банка» | **Частично** | В 0.11 этого нет: непотреблённый Opout на потраченном силе = мёртв навсегда (единственная стратегия FirstOpretOrTapret, operations.rs:304-307; grep «fallback» по крейту пуст). Автоперенос — это и есть fallback-seal (сценарий RFC #7 «assignment not spent»), т.е. изменение консенсуса, не трюк контракта. И даже с ним: пассивный держатель для доказательства владения должен получить от банка non-publication-proof на КАЖДЫЙ батч с момента своей последней подписи — неинтерактивность подписи куплена вечной зависимостью от публикации банком данных. |
| «Двух софтфорков достаточно» | **Опровергнуто как достаточность** | Классификация верна: оба — изменения RGB-валидации, не Bitcoin-софтфорки. (1) Fallback-силы = RFC #7 / RCP-240406A (github.com/RGB-WG/RFC/issues/7) — принят (S-accepted, milestone v0.12); в 0.12 отгружены только структуры (`TxoSealExt::Fallback`, bp-core seals/txout.rs:321-354), enforcement заглушен: `is_fallback()` = false, `verify_fallback()` = Ok(()), «TODO v0.13» — а линия 0.12 мертва с ~июля 2025. Критично: ветка fallback-по-burn неадъюдицируема без DA (проверить невключение = вскрыть сокрытый коммит). (2) RGB-HTLC: хеш-ветка выразима, таймаут-ветка невозможна в VM (0.11 и 0.12) → refund исполним мгновенно, атомарность рушится. Истинный счёт: два изменения RGB-консенсуса + один доверенный публикационный слой, который никаким «софтфорком» не даётся. |
| «Межбанк: LN/HTLC мелкое, on-chain батчем крупное» | **Частично** | Крупное on-chain — работает уже сейчас БЕЗ HTLC: два транзита в одном общем witness-tx атомарны по построению (LNP-BP discussion #125, dr-orlovsky: таймлоки не нужны). LN-нога — только через доверенную защёлку (у нас это отгруженный HODL-invoice-латч, [LIGHTNING.md](../LIGHTNING.md)) либо гибрид: RGB-хеш-лок на claim + таймаут на уровне якорения — пре-подписанные timelocked witness-tx (паттерн Spilman/statechain). У нас этот «уровень якорения» имеет две формы, и для банка важна вторая: обычная монета лестничная — TES-R-тиры на ОТНОСИТЕЛЬНЫХ CSV ([PROTOCOL.md](../PROTOCOL.md) §5.2); RGB-носитель намеренно НЕ лестничный (плоский спенд тира уничтожил бы аллокацию — правило terminal-freeze, §5.10), он держит signed-once backup-цепочку с абсолютным nLockTime. То есть таймаут-ветку для RGB-ноги банка придётся строить именно на пре-подписанных абсолютных локтаймах поверх цветного спенда, а не на CSV-тирах. ВАЖНО: скриптовый таймлок на самом общем UTXO — нельзя: refund-спенд закрывает силы ВСЕХ со-батченных клиентов без коммитов → их активы гибнут (validator.rs:440-495, восстановления нет). |
| «Один общий консаймент на всех» | **Подтверждено с пределом** | Артефакт уже существует и мал: input_map бандла (+MPC-якорь). Публикация связывает: один MPC-лист на контракт на witness → два конфликтующих консаймента вычислительно невозможны, эквивокация детектируема. Но сокрытие on-chain неотличимо от несуществования — митигция работает только пока данные текут; остаток — чистое доверие к DA банка (ровно S36/S37 из pop-ledger SPEC.md). |
| «TEE с ключом банка и publish-to-storage как условием подписи» | **Подтверждено (= statechain-доверие)** | Буквально наша модель SE: неаттестуемый энклав, которому доверяют исполнение негатива о поведении оператора ([TRUST-MODEL.md](../TRUST-MODEL.md) §3 — T-SE-1, и §7 — B1). Отличие: TEE держит ЦЕЛЫЙ ключ банка (роль клиентской доли играет owner-sig-замок), охраняет burn/DA, а не кражу; «публикация случилась» внутри энклава упирается в Sybil-устойчивость стораджа → федерация или Bitcoin-якорение (= снова pop-ledger). Операционное предупреждение из нашего же опыта: SGX-лейн нетестируем локально, фиксы попадают мимо него (кейс P0-1 secnonce). |
| (про 0.12) «CellLock решает» | **Частично** | Структура идеальная: `StateCell.lock: Option<CellLock>{aux, script}` + пер-входной witness + двухфазная верификация (ultrasonic state.rs:296-335, codex.rs:161-263). Но: ISA zk-aluvm — только полевая арифметика (Test/Eq/Add/Mul…), нет хешей/EC/подписей → «owner must sign» из коробки не реализуем (реалистичный обход — Winternitz-OTS над Poseidon-классом хеша, «учебник», не готовая либа); rgb-std жёстко ставит `lock: None` (popls/bp.rs:679); 0.12 консенсус-несовместим с 0.11 (перевыпуск всех контрактов) и линия мертва, тогда как форк rgb-protocol 0.11.1 живой (rc.11 от 2026-07-17) — на нём наш стек. |

## 3. Матрица атак банка

| Атака | Чем закрывается | Уровень | Статус |
|---|---|---|---|
| **Кража** (в т.ч. компрометация Bitcoin-ключа банка) | Схема «pubkey в owned state + ldp+vts»; каждый владелец — свой транзит в бандле | Контракт 0.11, сегодня | Закрываемо; схему надо написать (PFA как шаблон — НЕ годится as-is: глобальный ключ = кража банком) |
| **Точечный burn** (пропуск одного клиента) | Доказательство: старый консаймент жертвы + input_map любого со-получателя (циркулирует принудительно). Восстановление: только fallback-seal (RFC #7) | Доказуемость — «соц. слой» поверх 0.11 (кросс-обмен консайментами); восстановление — изменение консенсуса RGB | Доказуем при честном пропуске; **обходится стаффингом input_map** (фиктивный OpId) → полный фикс требует DA |
| **Глобальный burn + тотальное сокрытие** | Только принуждение к публикации ДО/В момент spend: PoP-якорение / TEE-гейт / федерация. Fallback-силы одни — неадъюдицируемы | Внешнее допущение о DA (никакое изменение RGB не помогает) | Не закрыт в концепции as-specified; главная дыра |
| **Заморозка / цензура одного клиента** (не включать его exit в батчи) | Owner-sig нерелевантен (закрыть сил может только банк). Нужен timeout-fallback на заранее объявленный клиентский outpoint ИЛИ Bitcoin-слой: пре-подписанные exit-деревья (наш паттерн — пре-подписанная и НЕ вещанная цепочка выхода на каждого владельца) | Изменение консенсуса RGB (fallback) или Bitcoin-слой (пре-подписанные exits) | Не закрыт ни одним ингредиентом из чата; ниже нашей планки «freeze ≠ seize» ([TRUST-MODEL.md](../TRUST-MODEL.md) §3, T-SE-2) |
| **Шантаж комиссией на выходе** | То же, что заморозка: без одностороннего выхода каждый exit — заложник спенда банка | Те же | Не закрыт |
| **Эквивокация** (разным клиентам разные версии батча) | Невозможна криптографически: один MPC-лист на контракт на witness + BundleId | Консенсус 0.11, бесплатно | Закрыт |

## 4. Что уже построено у нас

- **pop-ledger** (`~/Claude/pop-ledger`, github.com/gofman8/scv-pop; SPEC.md, все 47 пунктов, адверсариально проаудирован; интеграция в rgb-lib на ветке `pop`). Концепция банка с добавленным DA-допущением изоморфна Todd-2017 поэлементно: цепочка UTXO банка = цепочка силов леджера, батч = запись M_i, owner-sig = аутентифицированное закрытие (S7), автоперенос пассивных = non-publication-proof на запись (S19), «только burn/цензура» = дословно S36/S37. Ключевое: pop-ledger уже решает то, что чат счёл невозможным — компактные доказуемые non-publication (SMT, `NonPublicationProof::{Absent,InvalidSig}`), first-closure-wins, атрибутируемая эквивокация через подписанные заголовки, Bitcoin-якорение каждой записи. «Недоказуемый burn» структурно превращается в «оператор перестал выдавать пруфы» — цензура с подписанными уликами, а не двусмысленная потеря.
- **Utexo (mercurylayer)**: механика expiry без RGB-таймлока — пре-подписанные timelocked-транзакции. Это ОДИН протокол с ДВУМЯ формами монеты, обе актуальные ([PROTOCOL.md](../PROTOCOL.md), «One protocol, two coin shapes»; поля `deposit_protocol_version` и переключателя `UTEXO_PROTOCOL_DEFAULT` больше нет — `claim()` строит лестницу каждой свежей подтверждённой ROOT-монете безусловно):
  - **Лестничная** — каждый обычный BTC-депозит. TES-R: `F ──▶ T` (TRIGGER, БЕЗ таймлока, подписан один раз при депозите) `└▶ X_m` (EXTENSION, ОТНОСИТЕЛЬНЫЙ CSV `E_m`; продление заменяет его «горизонтально») `└▶ S_k` (STATE, ОТНОСИТЕЛЬНЫЙ CSV `Δ_k`, декрементится на каждом переводе). Все три тира — v3/TRUC с P2A-якорем, пре-подписаны и **НЕ вещаны**. BIP-68-относительные локи начинают считать только после подтверждения РОДИТЕЛЯ, а у `T` таймлока нет → **пока никто не вещал `T`, не созревает ничто: простаивающая монета не стареет вообще**. Календарного дедлайна нет, idle-rent = **0 vB** (PROTOCOL.md §2 — именно ради этого выкинута абсолютная лестница). Перевод со-подписывает свежий state на одну δ НИЖЕ заменяемого (replace-by-lower-timelock), так что state нового владельца всегда созревает первым, а старый раскрывается как superseded и учитывается переписью получателя. Продление (extension с меньшим CSV) и rollover (свежий уровень) — офчейн и неограниченны, монета живёт офчейн сколько угодно (`sdk43`). `refresh` — это примитив **ПЕРЕЯКОРЕНИЯ** (одна on-chain tx: монета переезжает на свежий funding outpoint и получает новую лестницу), а не сброс дедлайна (`sdk30`).
  - **Не-лестничная** — **RGB-носитель лестницы не получает никогда** и намеренно: плоский спенд тира уничтожил бы аллокацию (правило terminal-freeze, [PROTOCOL.md §5.10](../PROTOCOL.md), `sdk52`); и sub-coin, чей фандинг не вещан, не может укоренить триггер. Эта форма держит signed-once backup с абсолютным декрементирующимся nLockTime и передаётся handover'ом backup-цепочки — путь несущий для RGB-активов, а не наследие. Для RGB-банка релевантна именно она: у цветного выхода таймаут-ветка живёт на пре-подписанных АБСОЛЮТНЫХ локтаймах, календарный дедлайн у него сохраняется (`auto_exit_due`, `sdk34`), и «монета не стареет» на носитель НЕ распространяется.
  Односторонний выход = проход по пре-подписанной цепочке тир за тиром с выжиданием каждого относительного CSV, без единого обращения к SE (`sdk50`; `sdk45` — ту же цепочку прогоняет **бесключевая** третья сторона), а не «вещай backup и выиграй гонку». Это и есть недостающая «четвёртая опция» для таймаутов на общем UTXO (per-tenant exit-деревья vs невозможный общий скриптовый таймлок). Планка «freeze ≠ seize» с односторонним выходом (T-SE-2, [TRUST-MODEL.md](../TRUST-MODEL.md) §3) — то, чего у банка нет. [PROTOCOL.md §8.1](../PROTOCOL.md) — прецедент отклонения другой shared-UTXO-архитектуры (factories) по конфискационному классу.
- **Отгруженный прецедент «потомок, а не соперник»** (прямая аналогия для батча банка): неточные суммы платятся **in-ladder split** — тир состояния `SP` тратит `X_m.out[0]`, то есть ПОТОМКА триггера, а не соперника за `F`, и платит ребёнка-кусок + ребёнка-сдачу; порог допуска `min_child_value` = **1306 сат при 2 сат/vB** (ребёнок финансирует свои собственные два тира + dust) — `sdk58`, `sdk59`. Полученные дети **полноправны**: claim завершает штатную передачу ключа SE (получатель со-владеет `A_child`, инвариантным относительно ротации, поэтому пре-подписанная цепочка выхода остаётся валидной), отправитель заперт навсегда, а ребёнка можно платить дальше офчейн — целиком (`child_retransfer`) или дроблением (`child_in_ladder_pay`, цепочка ancestors глубины 2); одна со-подпись и одно раскрытое superseded-состояние на хоп, всё считает перепись получателя (`sdk60`: alice→bob→carol при неизрасходованном funding outpoint; `sdk17`: частичный второй хоп). Это ровно тот класс структуры, который банку нужен вместо соперничающих за общий UTXO выходов.
- **LN-опыт**: Lightning у нас работает В ОБЕ СТОРОНЫ поверх лестницы через защёлку на HODL-invoice ([LIGHTNING.md](../LIGHTNING.md); adaptor-сиги отвергнуты — PTLC в маршрутизирующей сети не существует): `sdk63` (pay), `sdk64` (receive), `sdk65` (неточный pay), `sdk67` (неточный receive), `sdk66`/`sdk68` (отказ и откат), `sdk19`/`sdk20`/`sdk24`/`sdk25` (адверсариальные), `sdk21` (удалённый SSP по HTTP). Уровень доверия — statechain-базовый, не trustless; LN-защёлкнутый кусок — единственный случай, который остаётся терминализованным (он висит незаклеймленным дольше окна pending-transfer-лока). Реалистичный шаблон для LN-ноги банка; trustless RGB-HTLC ждать неоткуда.
- **TEE-инфраструктура**: lockbox/SGX — готовая форма для TEE-митигции, но с известными ограничениями (нет клиентской аттестации; двухлейновый разрыв lockbox↔enclave/App), плюс энклав подписывает MuSig2/BIP340, а `Vts` требует ECDSA — нужен новый путь подписи.

## 5. Открытые вопросы для Адама

(Адам — автор RFC #7 / RCP-240406A, поэтому часть вопросов — прямо о его же предложении.)

1. **Fallback-адъюдикация без DA**: в RFC #7 ветка «closing tx provably doesn't contain any commitment / assignment not spent» — как downstream-верификатор fallback-клейма проверяет НЕвключение Opout, если банк скрыл input_map/MPC-раскрытие? Согласен ли он, что fallback-по-burn неверифицируем без внешнего слоя публикации, и что работает только fallback-по-таймауту?
2. **Стаффинг input_map**: подтверждает ли он, что бандл, мапящий Opout жертвы на фиктивный OpId, проходит валидацию у всех со-получателей (валидатор проверяет только known_transitions ⊆ input_map, без полноты/вскрываемости)? Планируется ли на линии rgb-protocol 0.11.x правило полноты или обязательной вскрываемости input_map?
3. **Со-получательское доказательство burn**: принимает ли он конструкцию «Opout ∉ input_map со-получателя + один MPC-лист на контракт на witness = публичное доказательство точечного burn» как корректную, и стал бы он закреплять обязательный кросс-обмен WitnessBundle между клиентами как протокольное правило банка?
4. **Таймлок-опкод на живом форке**: WitnessPos{height,timestamp} уже доходит до валидатора, но недостижим из скриптов (Vts его отбрасывает, op_contract.rs:492). Планирует ли rgb-protocol 0.11.x опкод чтения высоты witness (его же wish из RFC #7)? Как он видит reorg-безопасность валидации, зависящей от высоты?
5. **Схема per-owner Vts**: одобряет ли он паттерн «pubkey в per-allocation owned structured state + ldp + vts» как целевой; есть ли планы BIP340/Schnorr вместо ECDSA и >1 слота подписи на транзит (или официальная позиция: один владелец = один транзит в бандле)?
6. **Статус линий**: подтверждает ли он, что линия RGB-WG 0.12 (zk-aluvm/ultrasonic, CellLock без крипто-опкодов, fallback-пруфы отложены на «v0.13») фактически заморожена, и что фичи типа fallback-силов надо ждать/пушить именно в rgb-protocol 0.11.x? Если да — есть ли у него намерение перенести RCP-240406A на этот форк?
7. **Автоперенос пассивных**: как в его fallback-модели декларируется целевой outpoint переноса (в момент аллокации? витness-относительный сил на выход k закрывающей tx?) и как растёт размер пруфа владения пассивного держателя с числом батчей банка (наша оценка: линейно по всей активности банка, как S19 pop-ledger)?
8. **Expiry на общем UTXO**: согласен ли он, что скриптовый CSV/CLTV-refund на общем силовом UTXO недопустим (закрытие чужих силов без коммитов = массовый burn, восстановления в 0.11/0.12 нет), и что таймауты должны жить в пре-подписанных per-tenant exit-деревьях на уровне якорения?

## 6. Рекомендация

**Делать:**
1. Прототип схемы **per-owner Vts** (вариант PFA с pubkey в owned state) на нашем пине 0.11.1-rc.10 — это дешёво и закрывает «кражу» целиком; сразу заложить ECDSA-путь подписи в клиенте/энклаве.
2. DA-слой проектировать как **RGB-over-pop-ledger**: банк = оператор PoP-леджера, каждый батч = якоренная запись с доказуемой (не-)публикацией. Это превращает главную дыру (недоказуемый burn) в атрибутируемую цензуру с подписанными уликами — и у нас это уже написано и проаудировано. Минимальный промежуточный шаг до полного PoP: протокольно обязательный кросс-обмен WitnessBundle (input_map+anchor) между всеми клиентами батча.
3. Expiry/exit — только через **пре-подписанные timelocked exit-деревья** (наш паттерн), per-tenant, поверх co-signed spend'а общего UTXO; ветки клиентов должны быть **потомками** этого одного спенда, а не соперниками за него (наш in-ladder split — отгруженный прецедент). Это же даёт односторонний выход и возвращает планку «freeze ≠ seize». Учесть форму: для RGB-ноги таймауты — на пре-подписанных АБСОЛЮТНЫХ локтаймах поверх цветного спенда (у нас носитель не лестничный по terminal-freeze), относительные CSV-тиры годятся только для sats-ноги.
4. LN-ногу планировать как **HODL-защёлку** на statechain-уровне доверия (как наш отгруженный латч — обе стороны, [LIGHTNING.md](../LIGHTNING.md)), крупные межбанковские — joint-witness-tx атомарные свопы (LNP-BP #125), доступны уже сейчас.
5. Отправить Адаму вопросы §5, в первую очередь 1-3 (адъюдикация fallback и стаффинг input_map — от ответов зависит, нужен ли вообще консенсус-фикс или хватит протокольных правил + PoP).

**Не делать:**
- Не ставить скриптовый таймлок на общий UTXO (массовый burn со-батченных клиентов).
- Не ждать линию 0.12 и не строить на CellLock (нет крипто-опкодов, lock захардкожен в None в rgb-std, линия мертва, консенсус-несовместимость).
- Не форкать VM 0.11 ради таймлок-опкода в одиночку (раскол валидаторов); двигать через rgb-protocol upstream (вопрос 4 Адаму).
- Не продавать TEE-митигцию как нечто большее, чем базовое statechain-доверие (неаттестуемый энклав, целый ключ, наш собственный SGX-разрыв как предупреждение).
- Не принимать «двух софтфорков достаточно»: честный счёт — схема (есть) + fallback-силы (консенсус RGB) + публикационный слой (внешнее допущение; именно он несущий).
