# Mercury Utexo — production-readiness audit, 2026-07-30

Scope: `/Users/gofman/Claude/mercurylayer`, branch `feat/spark`, **working tree including uncommitted
changes** (the `transfer_many` in-ladder fix and `sdk69_transfer_many_inladder.rs` were audited as
part of the tree). Every citation below is from the current working tree.

---

## 1. Verdict

**NOT production ready. Do not deploy this to mainnet with real funds.**

The single sentence that decides it: **`verify_bundle_ex` — the client-side function that is the
entire anti-theft check for a conveyed TES-R ladder — derives every authority it checks from the
sender-supplied bundle itself (`clients/libs/rust/src/tesr.rs:1369`, `:1449-1452`), so a sender can
convey a self-signed decoy ladder that passes the census exactly, keep the real un-timelocked trigger
`T`, and take back 100% of any laddered coin they have already been paid for.** That is the default
coin shape (`claim()` ladders every plain BTC deposit unconditionally), the default payment path, and
it also gates the SSP's irreversible pre-payment Lightning census.

What would change the verdict: the fourteen critical findings in §2 fixed and each covered by an
adversarial E2E that fails before the fix and passes after. Six of them are one-to-three-line binding
or comparison fixes; three are deployment/build-config changes; the remaining five are structural
(child watchtower, clock reconciliation, latch↔transfer binding, RGB pre-pay gate, SE authentication).

Secondary, independently disqualifying: the shipped mainnet compose publishes an **unauthenticated**
statechain-entity signing API on `0.0.0.0:18080` with the SE master seed and Vault root token
hardcoded in the same file, and the SGX enclave that is supposed to be the production trust anchor is
built debug-launchable and signed with a test key committed to the repo. Any one of those three alone
means the deployment has no security properties at all.

## 2. Blocking findings

Ordered by severity, then by how cheaply they are exploited.

### C-1 — Conveyed root ladder is verified with ZERO binding to the coin (theft, total)

**Attack.** The sender of any laddered coin runs a patched client. It keeps the REAL ladder
`T → X → S` that `establish()` co-signed under the coin's real aggregate `A` (paying the sender), and
fabricates a decoy bundle: `agg_address` = a P2TR of a key the *sender* holds, `f_txid`/`f_vout`/
`f_value` arbitrary, `owner_exit_address` = the receiver's derived key, all tiers self-signed.
`verify_bundle_ex` computes `agg_spk = spk_of(bundle.agg_address)` (`tesr.rs:1369`) and seeds the
trigger sighash prevout amount from `bundle.f_value` (`tesr.rs:1448-1452`), so every
`verify_tier_cosigned` call checks the attacker's signatures against the attacker's own key and
succeeds. The census balances exactly, because the attacker burned the same number of real SE
co-signs on the ladder it retained. The receiver accepts, persists the decoy
(`transfer_receiver.rs:1127-1131`), and `wallet.rs:505-509` then suppresses establishing any real
ladder. The sender broadcasts the retained `T` — un-timelocked, spends `F`, this is [B1] — voiding the
receiver's flat backup, then `X`, then `S`, and sweeps the coin.

**Gain.** 100% of the transferred coin value, on every laddered transfer, deterministically.

**Second call site, arguably worse.** The identical unbound `verify_bundle` is the SSP's PRE-PAY
census (`clients/libs/rust/src/transfer_receiver.rs:410-420` → `ladder_census_ok`, consumed at
`clients/libs/rust-sdk/src/ssp.rs:431`). A decoy bundle sets `ladder_census_ok = true`, the SSP makes
an **irreversible Lightning payment**, and the sender then reclaims the coin with the retained `T`.
The comments at `transfer_sender.rs:255-262` and tests `sdk53`/`sdk63` assert this census blocks the
rob-SSP attack; it cannot, because it is self-referential. The code is the truth; those comments are
wrong.

**Aggravator.** The receiver gets no signal at all: `watch_pass` gates on
`outpoint_spent(&bundle.f_txid, bundle.f_vout)` (`tesr.rs:1117`) — the attacker-declared fake outpoint,
which is never spent — so the watchtower returns `vec![]` forever while the real `F` is consumed.

**Mitigated today.** Nothing. `cosign_detrigger` (`tesr.rs:1070`) could rescue a victim who manually
noticed `T` within `e0` blocks, but a repo-wide grep finds **zero** callers outside its own definition
— the only other hits are prose (`docs/utexo/PROTOCOL.md:391`,
`docs/utexo/learn/exits.md:148`, which falsely claims it is "proven end-to-end by sdk40"). The rescue
is unwired.

**Fix.** `verify_bundle_ex` must take the coin's authoritative aggregate and funding outpoint as
*parameters* and bind all four fields — exactly what `verify_child_bundle` already does at
`tesr.rs:1583-1604`. At the claim call site (`transfer_receiver.rs:706`) the correct sources are in
scope *at validate time*; note `coin.aggregated_address` is NOT — it is only assigned later at
`:1013`:

- `spk_of(bundle.agg_address) == tx0.output[tx0_outpoint.vout].script_pubkey`
  (`validate_tx0_output_pubkey`, already called at `:683`, has proven that output IS the true aggregate)
- `(bundle.f_txid, bundle.f_vout) == tx0_outpoint` (computed at `:638`)
- `bundle.f_value == tx0.output[tx0_outpoint.vout].value`

Binding only one leaves a variant (real `F`, attacker aggregate) passing. Apply the same at the SSP
pre-pay site. Additionally bind `bundle.params` and `bundle.network` to the server-served schedule
(see C-13).

### C-2 — Superseded tiers counted with no de-duplication: repeat a disclosed tier to mask a hidden co-signed state (theft, total)

**Attack.** The sender of a laddered coin has the blind SE co-sign ONE hidden rival — either `S*` over
`X_m.out[0]` at `csv = d_floor` paying the sender, or a rival trigger `T*` spending `F` outright.
`num_sigs` is now +1 over honest accounting. The sender then runs the normal transfer and, before
serialising, DUPLICATES the genuine superseded entry: `superseded_states = [S_old, S_old]`. Both
parse, both are txid-bound, both verify as genuine co-signs by `A`, both are in CSV bounds, both are
marked dead by the same contention. `verify_superseded_segment` returns `sups.len()` — the **vector
length**, not the number of distinct txids (`tesr.rs:1355`) — so
`expected = flat_backups + tiers + 2` absorbs the hidden signature and the census PASSES
(`tesr.rs:1500`).

**Gain.** With `S*`: the sender broadcasts `T → X_m → S*` at csv 144 while the receiver's `S'` sits at
1404 and loses the race by ~1260 blocks. With `T*`: `T*` spends `F` directly, killing both the
receiver's conveyed ladder and their flat backup — no race window at all. Full coin value.

**The pad is unbounded.** `k` duplicates absorb `k` hidden co-signs, so an entire rival sub-ladder can
be concealed. The same predicate feeds the ancestor lane (`tesr.rs:1708-1724`), the child lane
(`tesr.rs:1847-1861`) and the SSP pre-pay census, so in-ladder children and Lightning payouts are on
the same defect.

**Why this is a coverage gap, not an unforeseen class.** `clients/tests/rust/src/sdk55_backup_chain_adversarial.rs:6`
names this exact attack — "duplicate `tx1` inflates `expected` to absorb a hidden co-signed state" —
and proves it is rejected on the *sibling* term (`flat_backups`, guarded by INV-5 at
`lib/src/transfer/receiver.rs:329-335`). The adjacent term of the same equation was left open. The
comment at `tesr.rs:1429-1437` asserting class [S1] is closed is false.

**Fix.** One `HashSet<Txid>` in `verify_superseded_segment`, spanning `superseded_states` +
`superseded_extensions` + (defensively) the live tier txids, rejecting any repeat. All three lanes
share that function so it is a single-site fix. Do NOT use a count bound: the honest renew path
legitimately emits two superseded entries in one call (`tesr.rs:961-962`) and multi-hop children
accumulate one per hop (`tesr.rs:825`). Note the cross-list variant (one tx in both lists) is real but
conditional on the CSV lying in `[e_floor, e0] ∩ [d_floor, d0]`; the same-list duplicate is
unconditional and works on the first transfer of a fresh coin.

### C-3 — SE signing API is completely unauthenticated and published on the host in every compose file (theft + catastrophic availability loss)

**Attack.** Anyone who can open a TCP connection to the SE on 18080 — published to `0.0.0.0` by
`docker-compose-main.yml:45-46` (the mainnet stack), `docker-compose-tor.yml:47-48`,
`docker-compose-lockbox.yml`. Not one route in either SE implementation checks a credential, an owner
signature, a client cert, or a source IP.

1. **Census poisoning (no key material needed, cheapest, most damaging).** The census reads
   `num_sigs` from the enclave, not the coordinator DB (`server/src/endpoints/transfer_receiver.rs:44-66`),
   and `tesr.rs:1501` enforces EXACT equality. `lockbox/src/server.cpp:151-165` increments that counter
   on every successful partial signature. A stranger loops `/get_public_nonce` + `/get_partial_signature`
   over the statechain_ids handed out by the coordinator's own unauthenticated
   `GET /info/keylist` (`server/src/endpoints/utils.rs:139-144`). The partial sigs are useless to them,
   but every coin's census now fails at every receiver, forever: **total, permanent freeze of
   off-chain transferability system-wide**, recoverable only by a per-coin on-chain re-anchor.
2. **Mass forced exit.** `curl -XDELETE http://se:18080/delete_statechain/<id>` destroys the SE key
   share for any coin (`lockbox/src/server.cpp:413`). The coordinator gates the same operation behind
   single-use owner auth (`server/src/endpoints/withdraw.rs:39`); going direct erases it. Every user is
   forced into a simultaneous unilateral exit — a fee-market stampede. Principal is not burned (exits
   are pre-signed) but late exiters lose to congestion.
3. **Permanent brick.** Unauthenticated `/keyupdate` (`lockbox/src/server.cpp:373`,
   `enclave/App/App.cpp:80`) with attacker-chosen `t2`/`x1` rotates the share to something that no
   longer aggregates to the funding key. Not theft — the attacker cannot derive the new share — but
   un-co-signable forever, and indistinguishable from a legitimate rotation.
4. **Off-chain double-spend (theft).** Every anti-double-spend rule lives in the COORDINATOR:
   `single_use && finalized >= 1 → refuse` (`server/src/endpoints/sign.rs:97`, `:287`), spend budget
   (`:111`, `:294`), and the pending-transfer lock (`:148`, `:324`). The SE knows none of them. A
   *current owner* (this half needs a client key share, so the attacker is a user, not a stranger)
   pays Bob through the coordinator, then calls `/get_public_nonce` + `/get_partial_signature`
   DIRECTLY on the SE to co-sign a conflicting spend and settles that one. This extends beyond RGB
   sub-coins: bypassing `has_open_transfer` lets a sender co-sign a lower-CSV rival during any
   ordinary transfer's open window and steal the coin back from the in-flight receiver.

**Both lanes, worse on the shipped one.** `lockbox/src/server.cpp:290-431` — zero auth on six routes.
`enclave/App/App.cpp:60-114` — zero auth on eight, including `/add_mnemonic` and `/add_secret`. This
is a shared design gap, not a lane divergence.

**Fix.** Mutual TLS or a shared secret between coordinator and SE on every route; remove the `ports:`
publication from all compose files (`docker-compose-hw.yml` and `docker-compose-sim-prd.yml` already
omit it for the enclave — follow that); and move the single-use / spend-budget / open-transfer gates
into the SE so a coordinator bypass cannot defeat them.

### C-4 — SE master seed and Vault root token hardcoded in the repo, wired into the MAINNET compose, with the DB they decrypt published on postgres/postgres (theft)

**Attack.** Anyone who has read the repo. `docker-compose-main.yml` is the only compose with
`BITCOIN_NETWORK: mainnet` (`:53`, `:75`). It runs Vault in dev mode with root token
`2bbz80mr1zm0tfrjwxyq7f48ofgky848` (`:6`, `:40`) and writes the SE seed
`8b10a037120cf37441bd7623da2aa488c21889017ffb4f4d303b9dbcbada5bee` into it (`:20`). That 32-byte value
IS the AEAD key for every server key share at rest: `lockbox/src/server.cpp:277` loads it and
`lockbox/src/enclave.cpp:79` passes it verbatim as the ChaCha20-Poly1305 key (`crypto_aead_lock` at
`:27`) — **no per-coin KDF, and `ad = NULL` so a ciphertext is not even bound to its statechain_id**.
The same file publishes the lockbox Postgres on the host at 5433 with `POSTGRES_PASSWORD: postgres`
(`:104-107`) and Vault on 8200 (`:7-8`).

So: connect to 5433 with postgres/postgres, `SELECT sealed_keypair FROM generated_public_key`, decrypt
with the seed from the repo, and you hold the SE share `s` of every coin.

**Gain.** The aggregate is a plain EC sum — `user_pubkey_share.combine(&server_pubkey_share)`
(`lib/src/deposit/mod.rs:167`), with `new_blinded_without_key_agg_cache` (`lib/src/transaction.rs:598`),
and `key_update` preserves `s+o` (`lockbox/src/enclave.cpp:205-243`). Therefore **`agg_secret = o + s`
is a permanent constant for the funding output across every transfer**: one read of `sealed_keypair`
at any single moment while you own the coin yields the forever-key for `F`. Deposit → one `SELECT` →
sell the coin off-chain → sweep. No scraping infrastructure needed. Write access additionally lets you
forge `sig_count` (`db_manager.cpp:371`, `:472`) and defeat the census.

**Also leaked in the same file.** `docker-compose-main.yml:88` — the SE's nostr identity secret
(`nsec1...`), which signs the SE's directory listing: anyone can impersonate the SE in discovery.

**Not confined to that file.** Same constants in `docker-compose-lockbox.yml:6,20,40`,
`docker-compose-tor.yml`, `lockbox/.env:26`, `lockbox/Settings.toml:24`, `web/.env`. All tracked, none
gitignored. The safe alternative (`filesystem_key_manager.cpp:37-60`, random 32-byte seed, chmod 600)
is the `Settings.toml` default that the composes explicitly override.

**Lane.** Lockbox only — the SGX lane derives its seed in-enclave via Shamir shares
(`enclave/App/sealing_key_manager/sealing_key_manager.cpp:116-160`). But `docker-compose-main.yml:32`
pulls `mercurylayer/lockbox:latest`: **the sole mainnet compose ships the non-SGX dev lane.**

**Fix.** Rotate the seed, purge all four literals from the tree and from git history, default
`KEY_MANAGER` to a real KMS/HSM, refuse to boot on a known-bad seed or a dev-mode Vault when
`BITCOIN_NETWORK=mainnet`, add per-coin key derivation and bind the AEAD to the statechain_id as
associated data, re-encrypt every existing `sealed_keypair` row, and remove the published DB/Vault
ports.

### C-5 — Shipped SGX enclave is built debug-launchable and signed with a test key committed to the repo (theft; SGX confidentiality is zero)

**Attack.** The production image builds `SGX_DEBUG=0 SGX_MODE=HW SGX_PRERELEASE=1`
(`enclave/Dockerfiles/HW/Dockerfile:59`). PRERELEASE sets `-DNDEBUG -DEDEBUG` (`enclave/Makefile:79`),
which is exactly the combination for which `SGX_DEBUG_FLAG` is 1, and `enclave/App/App.cpp:141` passes
it straight into `sgx_create_enclave`. `Enclave.config.xml:8` leaves `<DisableDebug>0</DisableDebug>`,
so the SIGSTRUCT *permits* the debug attribute — meaning **a host attacker can EINIT the enclave with
the debug bit set even from a correct `SGX_PRERELEASE=0` build**. Fixing only `Dockerfile:59` would not
fix this. A debug enclave's pages are readable/writable by the untrusted host via EDBGRD/EDBGWR: dump
the unsealed master seed and every in-flight `secp256k1_keypair` out of enclave memory.

Independently, `enclave/Makefile:252` signs unconditionally with
`enclave/Enclave/Enclave_private_test.pem`, **checked into the repo**, so MRSIGNER is publicly known
and anyone can build a same-MRSIGNER enclave and `sgx_unseal_data` a stolen `node.sealed_seed`. (Note:
SGX sealing keys are CPU-fused, so this second vector requires running on the same physical host — it
lowers the bar from "debug a running enclave" to "run your own enclave on that box", it does not make
the seed file portable.) ProdID 0 / ISVSVN 0 (`Enclave.config.xml`) additionally means no sealing
rollback protection and no product separation.

**Gain.** With the seed, every `sealed_keypair` decrypts (`Enclave.cpp:31-49`), yielding every SE key
share. Combined with any party who holds an `o` for that epoch — the previous owner of a coin they
already sold — that is the full funding key. Note `update_sealed_keypair` overwrites in place
(`db_manager.cpp:527-543`), so recovering *pre-rotation* shares needs continuous access (live memory
reads, MVCC dead tuples, WAL, backups) rather than one dump; a rogue operator trivially has that.

**No attestation anywhere.** Grep for `sgx_ra_`/quote/attest over `enclave/App`, `enclave/Enclave`,
`server/src` returns only vendored CLI11/toml false positives. Neither the coordinator nor any client
ever checks the DEBUG bit, MRSIGNER, ProdID or ISVSVN. **Even a correct HW_RELEASE build signed with a
properly held key would give clients zero assurance** — remediation must include attestation, or the
SGX claim must be dropped from the trust model entirely. `README.md:5`'s assertion that the enclave
"ensures secure key share deletion" is falsified by this build config.

Also worth checking before deploy: `docker-compose-sim-prd.yml:7` (name implies production) builds the
SIM Dockerfile — pure simulation, no hardware protection at all.

**Fix.** Build via the `HW_RELEASE` target (`Makefile:178-182`) with a real signing key held offline;
set `<DisableDebug>1</DisableDebug>`, a non-zero ProdID and a real ISVSVN; remove
`Enclave_private_test.pem` from the tree and history; implement remote attestation in the coordinator
and expose the quote to clients.

### C-6 — `/transfer/unlock` verifies the receiver-side signature against a CALLER-SUPPLIED public key (theft + atomicity break)

> **FIXED 2026-08-11.** `/transfer/unlock` now looks up `statechain_transfer.new_user_auth_public_key`
> and refuses unless the supplied key IS it (`supplied_key_is_the_recorded_recipient`, compared as
> PARSED keys so one key's several spellings all work). Four tests, including the attack verbatim —
> a valid, self-consistent throwaway keypair is refused — and the opposite-parity near-miss.
> The earlier "external review finding 1" fix closed only the *missing*-key hole; the supplied key
> was still never compared to stored state, so this stayed live until now.

**Attack.** `server/src/endpoints/transfer_receiver.rs:138-141`:

```rust
Some(pk) => crate::endpoints::utils::validate_signature_given_public_key(&signed_statechain_id, &statechain_id, pk).await,
```

`pk` comes straight out of the request body and `validate_signature_given_public_key`
(`server/src/endpoints/utils.rs:41-57`) verifies the signature **under that same key**, with no DB
lookup. It is never compared to `statechain_transfer.new_user_auth_public_key` — which sits in the same
row and is already read by `get_auth_pubkey_and_x1` (`server/src/database/transfer_receiver.rs:144-172`).
So anyone who knows a statechain_id generates a throwaway keypair, signs the id, and clears that
transfer's `locked` bit.

**Theft (malicious SSP, LN RECEIVE — the direction documented as needing no operator trust).** The SSP
issues the HODL invoice, latch-transfers coin `C` to the user, waits for the payer's HTLC to reach
Claimable, clears `locked2` legitimately as registered owner, then clears `locked` by forging the
receiver side. `update_unlock_transfer` sees both bits clear and flips `lightning_latch.locked = false`
(`server/src/database/transfer_receiver.rs:299-313`), which is exactly what `get_preimage` requires
(`server/src/database/lightning_latch.rs:61-67`). The SSP retrieves the preimage and settles the HTLC.
Payer paid, receiver got nothing, SSP kept the coin. **The SSP does not need a companion bug** — it can
simply never post a usable `encrypted_transfer_msg`, since nothing on the preimage path checks the
receiver could ever have claimed.

**Atomicity break (batch participant, plain non-Lightning swap).** For a plain batch,
`insert_new_transfer` sets `locked=true, locked2=false` (`server/src/database/transfer_sender.rs:151-159`),
so `locked` is the ONLY gate `is_all_coins_unlocked` checks (`server/src/database/transfer.rs:30-50`).
A counterparty who never posts a valid transfer message clears their own row with a throwaway key,
honest parties unlock theirs, the batch reads unlocked, and the cheat claims their incoming coin. The
all-or-nothing property of coinswap batches is defeated.

**Griefing.** `update_unlock_transfer` also sets `updated_at = NOW()`, and `has_open_transfer` keys its
1-hour expiry on `updated_at`, so polling `/transfer/unlock` pins `has_open_transfer` TRUE forever and
denies the coin any SE co-signature. Scope note: this works only on `batch_id IS NULL` rows, because
the batch clause is keyed on `batch_time`, which unlock never refreshes.

**Correction to two claims that circulated during review:** `GET /transfer/batch_statechains/<batch_id>`
(`server/src/endpoints/lightning_latch.rs:55-59`) reads only the `lightning_latch` table
(`server/src/database/lightning_latch.rs:166-170`), so it does **not** enumerate plain-batch members.
The realistic attacker is a batch participant or the SSP, not an arbitrary internet host. And
`/transfer/transfer_preimage` (`lightning_latch.rs:118-126`) uses the same validator but is NOT
vulnerable — there the supplied key is subsequently the DB lookup key
(`sender_auth_xonly_public_key = $2`), so it is bound to stored state.

**Mitigated today.** Nothing. `sdk12_adversarial.rs:203-237` tests only the bad-sig + NULL-key case,
i.e. the half that was previously fixed; the self-signed-key case is untested. The comment at
`transfer_receiver.rs:131-137` documents fixing that different bug and is not evidence this one was
considered.

**Fix.** One comparison, and it must be a comparison, not a substitution (the receiver's key genuinely
is not yet in `statechain_data` at unlock time — see the client comment at
`clients/libs/rust/src/transfer_receiver.rs:983-984`):

```rust
let expected = get_auth_pubkey_and_x1(pool, &statechain_id).await?.0;
Some(pk) if pk == &expected => validate_signature_given_public_key(...).await,
```

Additionally, make `validate_signature_given_public_key` take the expected key from the DB everywhere
it is used, so the pattern cannot be reintroduced. And separately fix
`unlock_by_preimage` (`lightning_latch.rs:256`), which discards `update_unlock_transfer`'s `Result` and
returns HTTP 200 "Success" even when zero locks were cleared.

### C-7 — Sender-side freeze lapses at `batch_time + 20s` while the SSP's claim window is the 25-hour latch expiry (theft from the operator)

**Attack.** Any user doing a Lightning PAY swap, with one coin and one LN node they control (the RLN
fork supports HODL invoices).

1. Issue a self-invoice; `create_external_hash_latch` registers a latch with
   `expires_at = now + 90000s` (`server/src/endpoints/lightning_latch.rs:202`; classic RECEIVE latches
   are 3000s at `:88-93`); `/transfer/sender` writes the `statechain_transfer` row with
   `batch_time = now`.
2. The SSP runs every pre-pay gate (they pass — the coin is genuinely pending to the SSP and worth
   invoice+fee) and calls `send_payment` (`clients/libs/rust-sdk/src/ssp.rs:489`). The attacker's node
   parks the HTLC in Claimable.
3. At t = 21 s, **both** sender-side guards evaluate `batch_time > NOW() - batch_timeout` to FALSE:
   `has_open_transfer` (`server/src/database/transfer_sender.rs:67-77`) and
   `has_open_transfer_to_other_auth` (`:93-105`). `BATCH_TIMEOUT: 20` in **every** shipped compose
   including `docker-compose-main.yml:83` — and because `server_config.rs:208` is env-first, that 20
   always beats `Settings.toml:4`'s 120. The receiver-side claim window, by contrast, was deliberately
   moved onto the latch clock by audit [2]/H4 (`server/src/endpoints/transfer_receiver.rs:189-205`).
   **The two clocks differ by 4500×.**
4. A single `POST /transfer/sender` is already fatal: `validate_batch_transfer` takes the
   `is_batch_expired` branch and returns Success (`server/src/endpoints/transfer_sender.rs:43-51`), the
   re-address guard passes (`:149`), and `insert_new_transfer` **DELETEs the SSP's row including its
   `x1` and `encrypted_transfer_msg`** (`server/src/database/transfer_sender.rs:117`). The SSP's later
   `/transfer/receiver` gets an auth-key mismatch and is Forbidden.
5. The attacker settles the HTLC. The SSP's poll succeeds, `unlock_by_preimage` returns 200, `claim()`
   returns 0 transfers.

**Gain.** The full invoice amount, per swap, repeatably, at attacker-chosen timing.

**Why the SSP's on-chain fallback does not save it.** The SSP holds a co-signed `S'` paying its own
address (`clients/libs/rust/src/tesr.rs:1050-1063`) — but `peek_pending_transfers` persists nothing
(`tesr::persist` is only on the claim path), and the same lapsed window reopens the sign gate
(`server/src/endpoints/sign.rs:148`, `:324`) so the attacker co-signs a strictly-lower-CSV rival and
wins the maturity race. Note the required ordering: **co-sign the rival BEFORE re-addressing**, because
the re-address inserts a `batch_id IS NULL` row that immediately re-closes the sign gate.

**Lane split.** The non-exact in-ladder PAY lane terminalizes the latched piece
(`clients/libs/rust-sdk/src/transfer.rs:1204-1212`), which blocks the rival co-sign, so there this
degrades to forced on-chain recovery (griefing). The theft lives in the EXACT lane
(`ssp.rs:977-993`), and the attacker can force that lane deterministically by depositing a coin of
exactly amount+fee.

**RECEIVE direction is NOT the same.** Three reviewers independently confirmed: after an SSP
self-reclaim the new row has `batch_id` NULL, so `update_unlock_transfer` never clears
`lightning_latch.locked` (`server/src/database/transfer_receiver.rs:298-311`), `get_preimage` never
satisfies, and the payer's HODL HTLC is refunded. That direction is a failed swap / griefing, not
theft. Do not carry the "same asymmetry inverts" claim forward.

**Relation to known-open item 1.** This is that item, quantified, and **materially worse than
documented**: `docs/utexo/LIGHTNING.md:262-266` says "The risk is bounded in practice because the HTLC

### C-8 — SSP pre-pay gate never binds the latched coin's transfer to the latch batch (theft from the operator)

> **RE-VERIFIED OPEN 2026-08-11.** `create_external_hash_latch` still inserts a `lightning_latch` row
> with a caller-chosen `batch_id` and no cross-reference to `statechain_transfer`
> (`database/lightning_latch.rs:144`), so nothing binds the latch to the transfer that is supposed to
> deliver the coin. The preimage path gained an expiry refusal (audit [2]/H4) but not a membership
> one. Loss falls on the OPERATOR, not on users.

**Attack.** Any user with one coin `C` worth invoice+fee.

1. `create_external_hash_latch(C, H)` registers a `lightning_latch` row (statechain_id=`C`,
   batch_id=`B`, payment_hash=`H`). **Nothing binds `B` to any transfer**
   (`server/src/endpoints/lightning_latch.rs:182-207` lets any coin owner insert a latch row under an
   arbitrary batch_id with an arbitrary hash, with no cross-reference to `statechain_transfer`).
2. Transfer `C` to the SSP under a **different, non-latch batch `B''`**. `validate_batch_transfer` does
   not reject this: `get_latch_expiry_by_batch_id(B'')` is None, so the audit-[16] membership guard at
   `server/src/endpoints/transfer_sender.rs:71-78` is **skipped entirely**.
3. Hand the SSP `batch_id = B` and the invoice. `execute_pay` passes every gate: latch hash matches
   (`ssp.rs:380-388`); `get_statechain_ids_by_batch_id(B) = [C]` (`:397`); `C` IS in
   `peek_pending_transfers` because `get_statechain_transfer_messages` has no locked/locked2/batch
   filter (`server/src/database/transfer_receiver.rs:119-142`); census ok; value gate ok. **No gate
   anywhere checks `statechain_transfer.batch_id == B`.**
4. SSP pays (`ssp.rs:489`). Attacker collects.
5. SSP claims → `validate_batch(C)` reads `C`'s batch `B''`. `BATCH_TIMEOUT: 20` in every deployed
   compose means `B''` is already expired: `ExpiredBatchTimeError`
   (`server/src/endpoints/transfer_receiver.rs:203-206`). The SSP is blocked permanently. (A parked
   dust decoy coin in `B''` achieves the same via `is_all_coins_unlocked` but is unnecessary.)
6. Because `/transfer/receiver` never succeeds, `key_updated` stays false and the SE never rotated —
   the attacker still holds the share and the pre-signed exit. Optional cosmetic cleanup: re-transfer
   to a fresh own key once the expired-batch row stops blocking.

**Gain.** Full invoice amount per swap, deterministic, no race, no SE co-signature needed, marginal
cost ≈ zero.

**No race for the SSP to win.** `C`'s row is `locked=true` from insertion
(`server/src/database/transfer_sender.rs:151-155`), so background auto-claim cannot grab it first.

**Failure is silent.** `execute_pay`'s only backstop is `claimed == 0` (`ssp.rs:511-524`), but
`claim()` is wallet-wide (`clients/libs/rust-sdk/src/wallet.rs:564-568`), so on a busy SSP any
unrelated concurrent incoming transfer makes `claimed != 0` and `execute_pay` returns `Ok(preimage)`.

**Framing.** This is the exact INVERSE of audit [16]: that guard hardened "an uninvited coin joining a
latch batch"; this is "a latched coin joining a NON-latch batch", which the guard's own condition
structurally cannot cover.

**Fix.** Require `statechain_transfer.batch_id == latch.batch_id` for every latched coin — cheapest in
`execute_pay`, correct server-side in `validate_batch_transfer` (reject any transfer whose coin has a
live `lightning_latch` row under a different batch_id). The honest client already satisfies this
(`ssp.rs:977-995` uses one id for both), so the fix is non-breaking.

### C-9 — SSP's RGB pre-payment value gate never validates the exit branch or terminal ancestors (theft from the operator)

**Attack.** Any user of the SSP's Lightning PAY flow with an RGB carrier. She runs a patched client
that simply **skips one HTTP call** — `mercuryrustlib::lightning_latch::set_spend_budget`
(`clients/libs/rust-sdk/src/tokens.rs:614-620`) — or, equivalently, sends `terminal_parents = []`.
Either omission alone suffices. She colored-splits the carrier into a piece carrying the full invoiced
amount, latches it, and asks the SSP to pay.

The SSP's RGB gate (`clients/libs/rust-sdk/src/ssp.rs:437-475`) runs ONLY `validate_pending_token`,
which is pure RGB consignment arithmetic (`clients/libs/rust-sdk/src/tokens.rs:1362-1394` —
`validate_offchain_chain_info` + `accept_offchain_amount`, no `validate_branch`, no
`verify_terminal_parents`, no on-chain root check). The consignment is genuine so the gate passes.
`check_latched_coins` — the only consumer of the branch-validated sats `amount` — is called only in the
non-RGB `else` branch (`ssp.rs:481-485`), so the fact that `peek_pending_transfers` already set
`amount = 0` (because the branch/terminal check failed,
`clients/libs/rust/src/transfer_receiver.rs:333-364`) is silently discarded.

SSP pays (`ssp.rs:489`, irreversible). At claim time `validate_encrypted_message` runs
`required_terminal_ancestors` + `verify_terminal_parents`
(`clients/libs/rust/src/transfer_receiver.rs:646-664`) and rejects forever. Because validation gates
`process_encrypted_message` (`:122-128`), the SSP never even gets a key share for the piece — the
attacker keeps carrier AND piece AND the Lightning money.

**Not an edge case.** `latch_tokens` unconditionally routes through `colored_transfer` /
`colored_combine_transfer`, both of which mint the latched coin as an un-broadcast split/combine
output, so `funding_from_branch` is ALWAYS true on the RGB lane — the SSP's RGB gate therefore never
performs the branch check on any payment. `ladder_census_ok` passes trivially for a colored piece
(protocol_version < 2 → `(true, None)` at `transfer_receiver.rs:428-430`).

**Wider than "missing branch check".** `validate_pending_token` feeds only `tx.txid()` of each
sender-supplied branch tx into RGB validation (`tokens.rs:1373-1393`) — it never checks those
transactions are consensus-valid, fee-paying, or rooted in a confirmed unspent on-chain outpoint. The
gate has **no Bitcoin-layer grounding at all**; the attacker need not even perform a real split.

**Fix.** One line of dispatch: reject any latched coin with `p.amount == 0` regardless of lane, i.e.
run `validate_branch` + `verify_terminal_parents` on the RGB arm too, and call `check_latched_coins`
unconditionally.

### C-10 — Received in-ladder children have NO automatic or delegable exit protection; the sender's retained `S_0` sweeps the whole parent (fund loss)

**Attack.** The parent coin's owner (the sender of the in-ladder split). `in_ladder_split` discloses
the parent's old owner state `S_0` as superseded (`clients/libs/rust/src/tesr.rs:344`) — `S_0` pays the
SENDER's exit key and sits exactly `delta` blocks ABOVE `SP` over `X_m.out[0]`
(`tesr.rs:299-303`) — and the sender retains its signed hex plus `T` and `X_m`. Sender pays Bob a
child, then broadcasts `T` (no timelock, immediate), waits `E_m`, broadcasts `X_m`, waits
`sp_csv + delta`, broadcasts `S_0`: the **entire parent value** — every child's piece plus the
sender's change — lands at the sender's key.

**Bob's defence, and why he has none.** He must broadcast `SP → ext_child → state_child` inside the
`delta` window (36 blocks, ~6 h on mainnet, `lib/src/tesr.rs:122`). Every path skips children:

- `defend_ladders` (`clients/libs/rust-sdk/src/wallet.rs:782`) loads only `tesr::load`, i.e.
  `tesr-<sid>` keys; a claimed child is persisted under `ctesr-<sid>` (`tesr.rs:445-455`) — silently
  skipped. And `defend_ladders` is **not wired into `start_background`** at all
  (`wallet.rs:646-671`), for any coin.
- `auto_exit_due` → `estimate_exit_cost` → `get_backup_txs` errors (a child has no backup rows), so
  `Err(_) => continue` (`wallet.rs:708-713`, `:945-948`).
- `export_watch_bundle` bails at `if branch.is_empty() { continue }` (`watchtower.rs:94`) — a child has
  no `branch-<sid>` rows, so a DELEGATED keyless tower gets an EMPTY bundle.
- `coin_status::update_coins` (`coin_status.rs:272-297`) never chain-checks a CONFIRMED coin, so a
  polling wallet cannot even notice `T` confirming.
- `coin.locktime` is deliberately left `None` for an adopted child
  (`transfer_receiver.rs:925-928`), so no deadline is displayed.

**There is no reactive child primitive to build a loop out of.** `watch_pass` is safe to poll every
block because it early-returns unless `outpoint_spent(F)` (`tesr.rs:1114-1119`). `exit_child_pass`
(`tesr.rs:508-530`) has **no such gate** — it walks the chain from the trigger and broadcasts `T`
unconditionally. So the only automated posture available to a child holder is to force the coin
on-chain the moment they receive it, which destroys the entire off-chain premise. The fix is a missing
primitive plus wiring, not just wiring.

**Docs are wrong.** `wallet.rs:661-663` claims the auto-exit pass is "Default-on so an idle receiver is
protected without scheduling anything" and `:674-687` claims it protects "any owned OFF-CHAIN coin";
`watchtower.rs:1-25` claims the bundle covers "every off-chain coin"; `TRUST-MODEL.md:259-260` claims
keyless delegation works "in **both** coin shapes". All false for children. The code is the truth.

**Economics make this the payer's dominant strategy, not a gamble.** `SP` carries the attacker's own
change output, so losing the race returns their change intact; the only cost is ~450 vB of fees.
Positive EV at any success probability. With `transfer_many` now routed into `in_ladder_split`, one
`SP` carries N recipients, so a single ~372 vB exit defrauds all N — and the attacker's stake in any
RBF war is the SUM of all victims' children while each defender's is only their own.

**Broader than children (fix must cover this).** `export_watch_bundle`'s branch requirement also skips
laddered ROOT coins (they are funded on-chain and have no `branch-` rows), so the keyless WatchBundle
in practice covers only pre-TES-R shapes. `TRUST-MODEL.md:391`'s keyless-delegation claim is unbacked
for the entire laddered lane.

**Fix.** (a) Add `child_watch_pass`, gated on `outpoint_spent(F)` exactly like `watch_pass`. (b) Teach
`defend_ladders` about `ctesr-` keys and wire it into `start_background`. (c) Give
`export_watch_bundle` a laddered/child path that does not require `branch-` rows. (d) Populate a
deadline for adopted children so the UI can warn. (e) Have `verify_conveyed_child` refuse a child whose
parent `F` is already spent or whose `T`/`X_m` are already confirmed — today it fetches `F` with
`transaction_get` and never checks liveness (`tesr.rs:560-621`), so a sender can convey a child whose
parent ladder is already broadcast and blocks from `S_0` maturity, and the census still balances.

### C-11 — In-ladder split never re-persists the parent's bundle, and `defend_ladders` has no status filter — an HONEST sender's watchtower attacks their own payee (fund loss)

**Attack / accident.** `in_ladder_split` replaces the parent bundle's current state with `SP` and
pushes `S_0` onto `superseded_states` — but ONLY in the in-memory `parent_seg` clone
(`clients/libs/rust/src/tesr.rs:344-354`). `in_ladder_pay` (`clients/libs/rust-sdk/src/transfer.rs:1204-1237`)
and `in_ladder_pay_many` (`:1340-1373`) call `convey_child_bundle` + `persist_child` and **never** call
`mercuryrustlib::tesr::persist` for the parent. The only two `tesr::persist` call sites in the tree are
`wallet.rs:514` (establish) and `transfer_receiver.rs:1129` (adoption). So `tesr-<parent_sid>`
permanently still names `S_0` — paying the sender's own backup key, at the full pre-split value — as
the CURRENT state.

`defend_ladders` (`wallet.rs:774-799`) filters only on `duplicate_index != 0`. **No `CoinStatus`
filter.** It loads that stale bundle and runs `watch_pass`. The moment Bob starts his own exit,
`outpoint_spent` opens and the sender's client re-broadcasts `X_m` and then `S_0` every pass. A
malicious sender runs the loop and waits; an **honest** sender following the documented guidance
(`docs/utexo/learn/trust-model.md:50`, "call it per block from your loop") attacks their own payee
automatically, with no intent and no warning.

**The codebase already agrees the guard is required.** `unilateral_exit`'s explicit-id branch refuses a
non-CONFIRMED coin with the comment "kills the accidental-loss variant where an honest user exits a
spent parent and destroys their own payee's coin" (`wallet.rs:1049-1064`). Both `auto_exit_due` loops
filter `CONFIRMED` (`:702`, `:732`). `defend_ladders` alone does not.

**Scope is wider than in-ladder split.** The identical stale record exists after every WHOLE-COIN V2
transfer: `presign_receiver_state` builds `S'` for the receiver (`tesr.rs:1037-1064`),
`transfer_sender.rs:187` sets the coin IN_TRANSFER, and the sender's `tesr-<sid>` row is never updated
or deleted. **Every already-transferred laddered coin in the wallet is an armed automatic racer.** A
fix that only re-persists the parent on split leaves this instance live.

**Fix.** Add a `CoinStatus::CONFIRMED`-and-owned filter to `defend_ladders` (primary), AND re-persist
the parent bundle in `in_ladder_split`'s callers, AND delete/retire the `tesr-` row on whole-coin
transfer. Do all three; each closes a different half.

### C-12 — `withdraw()` on an in-ladder-split child broadcasts the trigger, then permanently bricks the exit (fund loss)

**Attack / accident.** The victim does the natural thing with a received child:
`wallet.withdraw(addr, Some([child_id]))` — or `withdraw(addr, None)`, which sweeps ALL confirmed
coins including every child. `wallet.rs:845-849` routes the child to `unilateral_exit` →
`exit_child_pass`, which can only broadcast the FIRST tier of the 5-tier chain
`T → X_m → SP → ext_child → state_child`: `X_m` carries a relative CSV so its broadcast fails and the
loop breaks (`clients/libs/rust/src/tesr.rs:526-529`). `withdraw` then **unconditionally** sets
`c.status = WITHDRAWING` (`wallet.rs:856`, ignoring `exit_child_pass`'s result) and reports success.

`status != CONFIRMED` (`wallet.rs:1059-1064`), the exit-everything path filters CONFIRMED
(`:1072`), `auto_exit_due` filters CONFIRMED (`:702`), `transfer()`'s spendable filter is CONFIRMED
(`clients/libs/rust-sdk/src/transfer.rs:105`) so the child cannot be paid onward either, and
`check_withdrawal` deliberately returns `Ok(())` without touching the status for exactly this coin kind
(`clients/libs/rust/src/coin_status.rs:155-163`). The coin is dead in every SDK direction.

**Compounding harm.** The trigger the victim just broadcast helps the sender: the sender retains `S_0`
(`tesr.rs:344`) at `sp_csv + delta` over the same `X_m.out[0]`, and the victim's SDK now refuses to
broadcast `SP`. The sender waits out the CSVs and takes the full parent value uncontested.

**Balance also silently vanishes.** A WITHDRAWING coin hits the `_ => {}` arm of
`compute_balance_excluding` (`wallet.rs:1356-1361`), so its sats disappear from `available_sats`,
`pending_sats` AND `in_transfer_sats` — no payout, no pending indicator.

**Recoverability.** The funds are frozen, not destroyed: the complete pre-signed chain lives in the
`ctesr-<id>` row (`tesr.rs:445-455`) and `state_child` already pays the victim's own key, so recovery
needs no SE and no counterparty — only a DB status reset or manual raw broadcast. There is no supported
path.

**Test coverage would report green.** `chaos22_concurrent_users.rs:743-751` selects "the first
CONFIRMED coin with a statechain_id" for its withdraw action, which CAN be a child — but
`chaos22_oracle.rs:208-247` only scans CONFIRMED coins for stuck value and books the withdraw as
`exited`, so the oracle structurally cannot see the brick.

**Fix.** Dispatch on child-ness in `withdraw` (the codebase already does at `wallet.rs:845`) and route
to a *repeatable* child exit driver; only set WITHDRAWING when the chain is actually complete; make
`check_withdrawal` able to resume a partially-broadcast child chain; and add a recovery entry point for
already-bricked children.

### C-13 — Client-supplied MuSig session bytes are never magic-checked: 133 bytes with a wrong header abort the coordinator process (and both SE lanes) (griefing, total outage)

**Attack.** Any user who owns one statecoin — or anyone who has ever observed a `signed_statechain_id`

### C-14 — Conveyed child reverts to sender control one hour after conveyance (payment reversibility; theft in the latched lane)

> **PARTIALLY FIXED, RE-VERIFIED 2026-08-11.** (a)'s re-address vector is closed:
> `has_open_transfer_to_other_auth` refuses a re-open addressed to a DIFFERENT key while the transfer
> is open, and a latch batch now stays open until `lightning_latch.expires_at` rather than 20 s (C-7).
> **What remains is the non-batch window itself** — a plain child conveyance keeps the 1-hour rule
> (`OPEN_TRANSFER_WINDOW_SQL`), so after 61 minutes an unclaimed conveyance is once again re-openable
> by the sender.
>
> The right fix is now available and was not when this was written: since `#133`, a sender who wants
> the coin back has an explicit, authenticated route — **cancel**, which re-points the child's row at
> the owner and discloses the orphaned co-sign. The lapse can therefore be removed for the child lane
> without wedging abandoned coins, because "I changed my mind" no longer needs a silent timeout to
> express. Left open deliberately rather than half-done: the window is ONE constant spliced into both
> halves of the lock (sender-side and re-address-side) precisely so they cannot drift, and changing it
> is a protocol-visible change to how long a payment stays irreversible.

**Attack.** The payer of an in-ladder split child pays Bob, receives goods off-protocol, then waits 61
minutes without Bob claiming (Bob's wallet not running — the normal case for a mailbox payment). Both
guards keyed on `updated_at > NOW() - INTERVAL '1 hour'` return false
(`server/src/database/transfer_sender.rs:70`, `:96`), the child's auth key is still the sender's
(`key_updated` never flipped), and the child is deliberately left NON-terminal on the plain lane.

(a) **Self-reopen:** `POST /transfer/sender` on the child sid with an attacker-controlled
`new_user_auth_key`. `insert_new_transfer` DELETEs the existing row **including Bob's encrypted mailbox
message** (`:117`) before inserting. The attacker completes `/transfer/receiver` itself and is again
first-class owner. Census-neutral — a key handover bumps no counter — and undetectable.
(b) **Rival:** `/sign/first` + `/sign/second` (the gate at `sign.rs:148` now passes) to co-sign a rival
child state one delta BELOW the conveyed one, then broadcast the chain. Beats even a Bob who cached the
bundle.

**Honest assessment of severity on the plain lane.** The v4 receive path completes the handover BEFORE
`persist_child` (`clients/libs/rust/src/transfer_receiver.rs:882-932`), so a compliant offline receiver
never owned anything — there is no protocol-compliant victim on that lane today. The correct framing is
**a mailbox payment is not final until claimed, and the payer can silently revoke after an hour, with
no record that a conveyance ever occurred**. That is a finality/UX hazard, and it becomes a live theft
vector the instant any flow surfaces a conveyed-but-unclaimed child as "received" — which
`peek_pending_transfers` already does for the latched SSP.

**Where it IS theft today: a protocol-version downgrade.** For `transfer_msg.protocol_version < 4` the
receiver takes the LEGACY branch (`clients/libs/rust/src/transfer_receiver.rs:833-864`): it calls
`persist_child`, sets `status = CONFIRMED`, pushes a "Receive" activity, and **never calls
`/transfer/receiver`** — no key handover, no auth rotation, `key_updated` stays false permanently.
`protocol_version` is a sender-chosen field inside the encrypted message
(`lib/src/transfer/sender.rs:170` sets 4 for honest senders; nothing on the receive path enforces a
minimum, and the v4-only transfer-signature check at `:606-630` is skipped too). A malicious payer
conveys at version 3: the receiver passes `verify_conveyed_child`, books the payment as received, and
the sender retains BOTH the child auth key and its SE share forever. One hour later the sign gate
reopens and the sender co-signs a rival. **The receiver did everything the protocol asks and loses the
piece, with no second census to catch it.** This is the version of C-14 that must be fixed first.

**Docs wrong.** `clients/libs/rust/src/tesr.rs:364-375` ([F1]) claims the lock "refuses every further
sender co-sign until the transfer completes — at which point the receiver's auth rotation makes the
lockout PERMANENT". The code gives that lock a 1-hour life with no completion requirement. (The
function's own doc comment at `transfer_sender.rs:53-59` does document the expiry and argues "no
victim: an unclaimed payment was never accepted" — so the expiry is a conscious liveness trade-off; the
[F1] comment is the one that is false.)

**Fix.** (1) Enforce a minimum `protocol_version` on the receive path and reject the legacy branch —
this closes the theft. (2) Tie the lock's life to `key_updated` rather than a wall clock, or terminalize
plain-lane children as the latched lane already does
(`clients/libs/rust-sdk/src/transfer.rs:1194-1209`, which carves that lane out precisely *because* "the
temporary pending-transfer lock does NOT cover" an unclaimed piece — the gap is known for LN and left
open for plain payments). (3) Do not silently DELETE a conveyed row; keep an audit record.

### H-1 — Root ladder's receiver-paying state has no value binding: `S'` can pay the receiver dust and the remainder to the sender (theft)

**Attack.** `verify_bundle_ex` checks only `output[0].script_pubkey` for **every** tier — trigger
(`tesr.rs:1391-1396`) and each intermediate (`:1417-1426`). No output VALUE is ever checked and extra
outputs are unrestricted (honest tiers already carry payload + P2A, so a third is unremarkable). The
blind SE co-signs any sighash.

- **Weaker variant (any sender):** hand-build `S'` with `out[0] = 330 sat` to the receiver,
  `out[2] = the rest` back to the sender. Census balances exactly. The receiver books the coin at full
  `tx0` value (`lib/src/transfer/receiver.rs:780`) and holds a real flat backup — so the sender
  broadcasts the retained `T` to void it, then `X`, then `S'`.
- **Stronger variant (a depositor, i.e. whoever ran `establish`):** skew the TRIGGER itself.
  `T` carries `TRIGGER_SEQUENCE = 0xFFFF_FFFD` (`lib/src/tesr.rs:160-162`, relative timelock
  disabled), so the sender takes `V − 330` in ONE confirmation, no CSV wait at all, and the entire
  downstream ladder is value-starved from the root with no renew able to repair it.

**Closing the receiver's escape.** The attacker sets `S'.csv = p.d_floor` (accepted: the bound check is
`csv < lo || csv > hi`), which removes the replace-by-lower-timelock counter — both
`presign_receiver_state` (`tesr.rs:1044-1049`) and `rollover` (`:1002-1008`) require
`cur_csv - delta >= d_floor` and refuse at the floor. Exhausting `e_floor` likewise kills `renew`.

**Precedent.** The identical hole was found and closed on the CHILD lane (`tesr.rs:1807-1821` binds
`st_out0.value` to the declared `out_value`, with a comment naming this exact spoof because "the blind
SE co-signs ANY output distribution"). The root ladder never got the fix.

**Fix.** Bind every tier: `out[0].value >= prevout_value - tier_fee - P2A_VALUE`, applied to `T`, each
extension, each state, and `SP`. Also note `verify_bundle_ex(.., final_is_split = true)`
(`tesr.rs:1418-1420`) skips even the scriptPubKey check on `SP`.

### H-2 — The exit-race margin is entirely sender-controlled: `TesrParams` travel inside the sender-supplied bundle, and the superseded check accepts a 1-block margin (theft)

**Attack.** Every CSV bound the receiver enforces is read from `bundle.params` — a
`#[serde(default)]` field of the conveyed JSON (`tesr.rs:80`) — and nothing cross-checks it against
`TesrParams::for_network` or an SE-served config (grep: no `TesrParams`/`params` reference anywhere in
`clients/libs/rust/src/transfer_receiver.rs`). The only relational constraint on the race is
`if sup.csv <= live_csv { reject }` (`tesr.rs:1317`) — a **strictly greater** CSV, i.e. a 1-block
margin, is accepted.

So the sender crafts `S_0` at CSV 145 and `SP` at 144 — both inside the honest mainnet
`[d_floor=144, d0=1440]`, so it works **without touching params at all**. Bob's window to broadcast `SP`
before `S_0` confirms is ONE BLOCK instead of the designed 36 (~6 h). Combined with C-10 (no child
watchtower), the sender wins with near certainty.

**With tampered params it is much worse.** `d_floor`/`e_floor` are sender-supplied too
(`:1296-1299`, `:1413-1416`, `:1766-1769`, `:1790-1793`); setting the floors to 0 with `seq = 0` passes
both BIP-68 bit tests and collapses the WHOLE exit to ~3 blocks. That deletes the attacker's only real
cost — up to ~5 days of capital lockup waiting out `E0 + D`. **This does not require a patched client:**
`transfer_sender.rs:305-311` loads the bundle from the sender's own wallet sqlite and
`presign_receiver_state` (`tesr.rs:1104-1108`) takes the margin from `bundle.params.delta` in that row.
Editing one JSON field in a DB you own makes the stock client emit a thin-margin transfer.

**Doc is false.** `lib/src/tesr.rs:88-91` — "no fund is at stake in getting them wrong — only exit-wait
length". The wait length IS the theft margin.

**Fix, and it is nearly free.** `network` is ALREADY bound end-to-end (`tesr.rs:1361-1370`, `:1575`
`require_network` against the receiver's own backup address), so
`TesrParams::for_network(&bundle.network)` is a drop-in with zero new inputs — the verifier already
holds the authoritative value it declines to use. Then add the relational check at `tesr.rs:1317`:
`sup.csv >= live_csv + p.delta`. **Both** are needed: the params check alone still admits the 145/144
pair; the delta check alone still lets the sender shrink δ. Correct the `lib/src/tesr.rs:89-91` comment
in the same change.

### H-3 — `PARENT_V2_BASELINE` is hardcoded to 1, so every in-ladder split of a RECEIVED laddered coin is unclaimable (fund loss / stuck payment)

**No attacker.** `verify_conveyed_child` always passes `PARENT_V2_BASELINE = 1` as the parent's
flat-backup count (`clients/libs/rust/src/tesr.rs:611`, its only use site; the constant is at `:437`
and its own doc comment concedes it assumes "the coin's on-chain deposit co-signs exactly ONE backup").
That is true only for a parent that was deposited and never transferred: every whole-coin hop co-signs
one more backup tx (`clients/libs/rust/src/transfer_sender.rs:285` →
`create_backup_tx_to_receiver`) plus the Model-A state (`:311`).

Alice deposits (sig_count 4 = 1 backup + 3 tiers), transfers whole to Bob (+2 = 6; Bob's receive check
passes because it correctly uses the CONVEYED `transfer_msg.backup_transactions.len()` = 2,
`transfer_receiver.rs:709`). Bob pays Carol a non-exact amount → `in_ladder_split` co-signs `SP` (+1 =
7). Carol computes `expected = 1 + 3 + 2 = 6 != 7` → "num_sigs mismatch … possible hidden state"
(`tesr.rs:1500-1505`). Carol can never adopt. Bob has already terminalized the parent, booked the piece
WITHDRAWN, and persisted only the change bundle.

**The error term equals the number of prior hops** — it is cumulative and never self-heals except via
an on-chain `refresh()` re-anchor, which mints a new statechain_id with a fresh count
(`clients/libs/rust-sdk/src/refresh.rs:184-206`). Duplicate deposits under the same statechain_id are a
second source. The correct framing is "parent `flat_backups != 1`".

**Also breaks the SSP pre-pay lane.** `peek_pending_transfers` calls `verify_conveyed_child`
(`transfer_receiver.rs:392-408`) and sets `ladder_census_ok = false`, so the SSP refuses to pay — but
only AFTER `in_ladder_pay` has terminalized the parent, co-signed `SP` and registered the latch. On the
LN lane the piece is deliberately terminal (budget 0), so the payer can never co-sign a rival to
reclaim it and the piece's only pre-signed path pays the SSP's exit key: the payer loses it outright.

**Direction of failure.** The constant only ever UNDER-counts (a laddered parent always has ≥1 flat
backup), so this is fail-CLOSED and is **not** a theft vector — it cannot absorb hidden state. Value is
theoretically recoverable (the mailbox row has no TTL, `get_msg_addr` is non-destructive, and
`child_state` pays the recipient's own key), but there is no supported recovery for either party.

**Why the suite is blind.** Every shipped in-ladder E2E (`sdk58`, `sdk59`, the new `sdk69`) splits a
coin the sender DEPOSITED, where baseline 1 happens to be correct.

**Fix.** Convey the parent's real flat-backup count inside `ChildTesrBundle`, bound to the conveyed
chain (not sender-declared — a sender-declared count would reopen C-2's padding), or derive it from the
parent segment. Reject on absence. Add an E2E that splits a twice-hopped parent.

### H-4 — `ensure_exact_coin` / `split_coin` do not dispatch on child-ness: a received child gets plain-split over its un-broadcast funding outpoint (fund loss)

**No attacker.** `transfer` was taught the three-way shape dispatch
(`clients/libs/rust-sdk/src/transfer.rs:168-200`) and `transfer_many` has just been taught it, but
`ensure_exact_coin` filters candidates ONLY on `tesr::load(...).is_none()` (`:644`), and `split_coin`
applies the same one-sided test (`:698`). A received child's bundle lives under `ctesr-<sid>`, so
`load` returns None and the child sails through. `sign_split_tx` then builds the spend from
`coin.utxo_txid`/`utxo_vout`, which for an adopted child is `SP.out[j]`
(`transfer_receiver.rs:923-924`) — an outpoint of an UN-BROADCAST tx.

**Both return paths are child-blind.** The finding is not confined to the splittability loop: the
**exact-match early return** (`transfer.rs:613-621`) will also hand back a child's statechain_id, and
both callers feed that straight to `mercuryrustlib::transfer_sender::execute`
(`ssp.rs:558-568` in `create_receive`, `ssp.rs:975-985` in `pay_lightning_invoice`), bypassing the
`load_child` dispatch at `transfer.rs:430` entirely. `clients/libs/rust/src/tesr.rs:764-766` documents
precisely this as invalid: "A received child cannot go through `transfer_sender::execute`: it has no
`tesr-` bundle (only `ctesr-`)".

**Consequences.** `split_coin` sets the child's spend budget to 1, burns it, marks the child WITHDRAWN
and registers two sub-coins. `register_split_subcoins_n` inherits the branch from `branch-<parent>`
(`:1586`) — a child has NO `branch-` row, so each sub-coin's exit branch is just the split tx, whose
input is not on chain. The sub-coins cannot be withdrawn and cannot be transferred (the receiver's
`validate_branch` requires an on-chain root, `transfer_receiver.rs:650-656`). Meanwhile
`unilateral_exit` REFUSES the now-WITHDRAWN child (`wallet.rs:1059-1064`), so its intact `ctesr` ladder
is unreachable. The wallet reports no error and the sub-coins re-enter the spendable balance — the
failure only surfaces at the counterparty.

**Reach.** Not SSP-only: `transfer(addr, non_exact_amount)` on a laddered coin conveys a piece child to
an ordinary RECIPIENT, and `claim()` ladders every plain BTC deposit, so the non-exact in-ladder lane is
the DEFAULT payment path. Any user calling the public `pay_lightning_invoice` can hit this. In
`create_receive` it additionally strands an in-flight swap: the SSP has already minted the preimage and
issued a HODL invoice (`ssp.rs:555-575`).

**Side effects even when it aborts.** `split_coin` performs `take_derived_tokens` and creates two
deposit slots BEFORE the co-sign that can fail, so a failed attempt permanently consumes 2 of the
parent's 64 lifetime derived-token slots.

**Fix.** Apply the same `load_child` probe used at `transfer.rs:168`/`:430` in BOTH of
`ensure_exact_coin`'s return paths and in `split_coin` — route to `child_in_ladder_pay`, or refuse.

### H-5 — Duplicate-transfer guard is dead for every non-batch transfer (`batch_id = NULL` never matches) (theft)

**Attack.** `exists_msg_for_same_statechain_id_and_new_user_auth_key` filters `AND batch_id = $3`
(`server/src/database/transfer_sender.rs:8-12`). For a P2P transfer `$3` is NULL and `batch_id = NULL`
is NULL — never true — so COUNT is always 0 and the guard **never fires**.
`has_open_transfer_to_other_auth` only blocks a DIFFERENT auth key. So a sender can re-POST
`/transfer/sender` with the SAME `new_user_auth_key` any number of times while the transfer is open;
each call runs `insert_new_transfer`, which unconditionally DELETEs the row (destroying the posted
`encrypted_transfer_msg`) and inserts a **fresh random `x1`** (`server/src/endpoints/transfer_sender.rs:165-168`).

**TOCTOU brick → sweep.** The receiver validates `t1` against the `x1_pub` fetched from
`/info/statechain` (`lib/src/transfer/receiver.rs:686-700`), then POSTs `t2`. If the sender rotates
`x1` in that window, `transfer_receiver` hands the enclave the NEW `x1` with the OLD `t2`
(`server/src/endpoints/transfer_receiver.rs:315-321`), the SE share is rotated by the wrong scalar, and
the aggregate no longer matches the funding output.

**And the receiver is left with nothing to exit with.** `get_new_key_info(...)?` at
`clients/libs/rust/src/transfer_receiver.rs:1009` returns `Err(IncorrectAggregatedPublicKey)`
(`lib/src/transfer/receiver.rs:765-767`) BEFORE `insert_or_update_backup_txs` at `:1034`, so the
receiver never persists the conveyed backup chain; the message it would need to retry was deleted in the
same re-open (`get_statechain_transfer_messages` filters `encrypted_transfer_msg IS NOT NULL`,
`server/src/database/transfer_receiver.rs:118-127`); and a retry hits the `is_key_already_updated`
short-circuit. Meanwhile the **sender retains its own fully-valid pre-signed ladder** under the original
invariant aggregate: broadcast `T`, wait out the CSV, sweep the full coin with no rival in existence.
The comment at `clients/libs/rust/src/transfer_receiver.rs:928-930` ("any failure above leaves the
message re-claimable rather than half-adopted") is false, because the sender controls deletion of that
message.

**Same shape on the child lane.** `get_new_key_info` at `:908` runs BEFORE `persist_child` at `:932`,
and `persist_child` is the ONLY persistence of the child's exit bundle — so a rotated `x1` leaves the
receiver with a claimed child and no exit transactions at all.

**Ransom lever.** Only the sender learns both `x1` and `x1'` (`transfer_sender.rs:172-174` returns `x1`
in the clear); the receiver sees only the pubkeys and cannot derive the correction scalar.

**Fix.** Replace `AND batch_id = $3` with `AND batch_id IS NOT DISTINCT FROM $3`. Separately, do not
rotate `x1` on a re-post for the same auth key (make it idempotent), and reorder the receive path so
backup/child persistence precedes or is transactional with the key update.

### H-6 — `POST /transfer/receiver` is check-then-act across the enclave call, and `keyupdate` is non-idempotent in BOTH SE trees (fund availability loss)

> **HALF FIXED 2026-08-11 — the coordinator half.** The claim path now takes the same
> transaction-scoped `pg_advisory_xact_lock` that `/sign/first` has always used, keyed
> `claim:<statechain_id>`, before `is_key_already_updated` and held past `update_statechain`. Two
> concurrent claims can no longer both read "not yet updated" and both reach `keyupdate`. Failure to
> take the lock is a `503`, not a pass-through.
>
> **Still open: SE-side idempotence.** Both enclave trees remain unguarded
> `load → key_update → update_sealed_keypair` with no compare-and-swap, so a coordinator that is
> bypassed, replaced, or run twice against one database can still double-rotate a share. The
> coordinator lock makes the race unreachable through the shipped path; it does not make `keyupdate`
> idempotent.

**Trigger.** `is_key_already_updated` is a bare SELECT at
`server/src/endpoints/transfer_receiver.rs:294`; the enclave `keyupdate` runs at `:346`; `key_updated`
is only written afterwards by `update_statechain` at `:371`
(`server/src/database/transfer_receiver.rs:226-253`). There is no advisory lock, no transaction, no
idempotence key — while `/sign/first` DOES take `pg_advisory_xact_lock` for exactly this class
(`server/src/database/sign.rs:11-21`). Neither SE guards: `lockbox/src/server.cpp:171-222` and
`enclave/App/statechain/transfer_receiver.cpp:19-100` are the same unguarded
`load → key_update → update_sealed_keypair`, and both DB writes are plain UPDATEs with no
compare-and-swap. `key_update` unconditionally computes `s_new = s_old + t2 - x1`
(`lockbox/src/enclave.cpp:237-250`, `enclave/Enclave/Enclave.cpp:335-348`). Applied twice, the
aggregate becomes `A + (t2 - x1) != A` and no longer matches the on-chain output.

**The race is real but narrow** — the second request's READ must land before the first's
`update_statechain` commit AND its SE call must serialise after the first's `update_sealed_keypair`
commit. A naive parallel burst mostly writes the same value harmlessly.

**The race-free path is the production-realistic one, and the finders under-weighted it.** The SE
commits its rotated keypair BEFORE the coordinator writes `key_updated`. Any dropped response,
timeout, coordinator crash, or the unguarded `serde_json` `.expect()` at
`transfer_receiver.rs:361` / `.unwrap()` at `:360` leaves `key_updated = false` with the tweak already
applied. An ordinary SEQUENTIAL retry then double-applies — no attacker, no concurrency. The client
reuses the same persisted coin so `t2` is byte-identical.

**Impact, honestly stated.** Not theft, and not principal loss: the pre-signed exit chain was signed
under the invariant aggregate and stays valid, so the cost is a forced unilateral on-chain exit plus
CSV delay. But note the caller whose request lands FIRST gets the correct pubkey, passes
`get_new_key_info` and banks a coin the SE can no longer sign for — so the corruption is not always
visible to the party that succeeded. The `auth_sig` is a plain schnorr sig over `t2` with no nonce and
no expiry (`:276-292`), unlike `withdraw`'s `validate_signature_nonce` — a standalone hardening gap.

**Fix.** An SE-side lock would NOT help (serialised double execution still rotates twice). Either a
per-transfer replay key inside the SE, or a coordinator-side conditional UPDATE that CLAIMS
`key_updated` before the enclave call and rolls back on failure. Add `pg_advisory_xact_lock` on the
statechain_id. Add a nonce to the receiver auth signature.

### H-7 — Every colored spend of a carrier's funding outpoint `F` is built without dispatching on ladder shape — the SEED class, unguarded in the RGB paths (fund loss)

**Attack.** `colored_transfer` (`clients/libs/rust-sdk/src/tokens.rs:628`), `colored_combine_transfer`
(`:910`) and `batch_transfer_tokens` (`:1156`) all construct a transaction spending the carrier's
funding outpoint `F`. None calls `mercuryrustlib::tesr::load` — `grep -n 'tesr::load'` over
`tokens.rs` returns nothing — whereas the plain-BTC sibling `split_coin` hard-refuses a laddered parent
for exactly this reason (`transfer.rs:698-705`).

The "a carrier is never laddered" invariant is enforced NOWHERE at the point of use — only best-effort
inside `claim()`'s establish loop, which degrades to "ladder everything" whenever the carrier set comes
back empty: `wallet.rs:467-473` returns `Some(HashSet::new())`, **not an error**, for a wallet with no
`rgb_data_dir`/`rgb_proxy_url` or an empty stash. `SdkConfig::mainnet()` ships with
`rgb_data_dir: None` (`config.rs:110-117`), and `import_recovery_bundle` (`wallet.rs:189-196`)
deliberately leaves the stash empty — so the documented recovery procedure manufactures the vulnerable
window.

**Deliberate variant.** Every input to the laddering decision lives on the sender's own machine. A
malicious issuer moves `rgb_data_dir`, calls `claim()` once so `wallet.rs:476-520` ladders their
issuance carrier, restores the stash, then calls `transfer_tokens`. They hold a fully co-signed
no-timelock `T` over `F`, and `tokens.rs:628` builds the colored split of that same `F`. After the
recipient validates the consignment and ships goods, the sender broadcasts `T`: `F` is consumed, the
split tx and its consignment are dead, the allocation is destroyed, and the ladder pays the sender the
full carrier value (`payee = coin.backup_address`, `wallet.rs:512`). `T` is v3/TRUC + P2A and
fee-bumpable forever versus a locktime-0 colored split with a frozen fee, so there is no race to win.
`colored_combine_transfer` is worst: one retained `T` on any of N inputs voids the whole combine.

**Accidental variant.** `unilateral_exit`'s exit-everything path filters carriers through the same empty
set (`wallet.rs:1069-1075`) and then runs `exit_pass`, broadcasting `T` (`:1086-1090`) — burning the
allocation with no adversary at all. (`defend_ladders` is NOT that route: `watch_pass` returns
immediately unless `F` is already spent, `tesr.rs:1117`.)

**The deeper sibling defect, worth its own item.** The piece recipient and the SSP census only the
PIECE's `num_sigs` (`transfer_receiver.rs:721`) and the CARRIER's `terminal` flag (`:538-575`), never
the carrier's `num_sigs`. Since `sig_budget` is NULL by default (`deposit.rs:225-245`) and the SE is
blind, ANY extra pre-budget co-signature on the carrier — a ladder trigger, or a hand-rolled rival spend
of `F` — is undetectable by the receiver.

**Fix.** Add the `tesr::load` refusal at all three colored spend sites, mirroring `transfer.rs:698`;
exclude carriers from `defend_ladders` and from `unilateral_exit`'s sweep by a positive marker rather
than an inferred set; make `token_carrier_outpoints` return `Err` (not `Ok(empty)`) when the stash is
absent or desynced; and census the carrier's `num_sigs` on the receive path.

### H-9 — An RGB allocation has no unilateral exit; the only pre-signed spend of a carrier is RGB-unaware (fund loss on SE failure)

**The gap.** The entire Mercury trust model rests on "you can always exit unilaterally with pre-signed
material". For RGB that property does not exist.

- `unilateral_exit` (`clients/libs/rust-sdk/src/wallet.rs:1039-1049`) and `withdraw` (`:815-825`) hard-
  error on any carrier ("move the asset off this coin first").
- `export_watch_bundle` structurally sets `backup_tx: None` for carriers
  (`clients/libs/rust-sdk/src/watchtower.rs:98-104`) — correct hardening, because the pre-signed backup
  is a plain `create_tx1` that would close the seal with no transition and burn the allocation.
- The only shipped alternative, `auto_exit_due`'s MATERIALIZE (`wallet.rs:727-759`), broadcasts the exit
  **branch** only: it settles the allocation at an on-chain outpoint that is still 2-of-2 with the SE, so
  onward movement still needs the SE. And it requires a `branch-<id>` row.
- **No colored exit exists in the public API.** `create_colored_backup_tx(is_withdrawal=true)`,
  `witness_receive`/`blind_receive`, and `refresh_rgb_anchor_self_transfer`
  (`clients/libs/rust/src/rgb.rs:494`) have **zero non-test callers** anywhere.
- `burn_tokens` (`tokens.rs:275-279`) only touches engine-held balance — "statechain-bound supply must
  be exited back into the engine first", with no such exit existing.

**Consequence.** If the SE stops co-signing (failure, censorship, compulsion), statechain-bound RGB is
frozen at a 2-of-2 outpoint, and the only pre-signed escape destroys it. There is also no COOPERATIVE
off-ramp even with a healthy SE — the error message both exit guards return points at an operation the
SDK cannot perform.

**Corrections to the finder's framing, for the record.** An issuance carrier is NOT exit-less: it holds
a stored plain `tx1` (`coin_status.rs:87`) recovering its packaging sats, and `issue_token` broadcasts
`fund_statechain` (`tokens.rs:147-153`) so its allocation is already on-chain-settled — its exclusion
from `auto_exit_due` is correct (no un-broadcast ancestor can race it), not a second hole. And a
received carrier's `branch-<id>` IS a pre-signed, SE-free, allocation-PRESERVING settle. So the accurate
statement is: **frozen, not burned** — and there is exactly ONE hole (no SE-independent colored exit),
identical for both carrier classes.

**Aggravator.** `docs/utexo/GRANULARITY-SPEC.md:480-484` instructs holders to broadcast stored rows
manually; a holder who pulls `get_backup_txs(id)` instead of `branch-<id>` burns their own allocation
with no guard in the way. `TRUST-MODEL.md:180-185` (T-SE-2) actively asserts the contradicted property.

**Fix.** Implement a colored exit path (pre-sign a colored spend at claim time so it exists without the
SE, or at minimum ship the cooperative `create_colored_backup_tx(is_withdrawal=true)` wrapper), correct
T-SE-2, and refuse to serve `get_backup_txs` for a carrier without a loud warning.

## 4. Known-open items carried forward

**(1) `lock_expiry` clock reconciliation — WORSE THAN DOCUMENTED. Now a blocking finding (C-7).**
`docs/utexo/LIGHTNING.md:262-266` calls it "a free option" and asserts "The risk is bounded in practice
because the HTLC CLTVs in use sit inside that window"; `docs/utexo/learn/lightning.md:148` says "~120s".
The shipped value is `BATCH_TIMEOUT: 20` in every compose including the mainnet one, and env beats
`Settings.toml`, so the real window is **20 seconds against a 25-hour latch — wrong by ~4500×**. Worse,
the residual contemplates only `has_open_transfer` and the two sign gates; it never contemplates
`has_open_transfer_to_other_auth` plus `insert_new_transfer`'s unconditional DELETE, which lets the
attacker repossess the coin **off-chain with no on-chain race at all** and destroy the SSP's claim path.
`LIGHTNING.md` §8's claim that the pre-pay census prevents robbing the SSP is falsified twice over (by
this and by C-1). Assessment: this is the top open item and the doc understates it in both magnitude and
mechanism.

**(2) `key_updated` bind on `get_preimage` — still unbuilt, and now less load-bearing than the hole
beside it.** RECEIVE still rests on coordinated-clock atomicity. But C-6 shows the receiver-side
`locked` bit — the thing the bind was meant to corroborate — is forgeable by anyone with a throwaway
keypair, so building the bind without fixing C-6 buys nothing. Fix C-6 first, then build the bind.
Note also that nothing binds the latch to the receiver's address at all: `insert_new_transfer` takes
`new_user_auth_key` verbatim (`server/src/database/transfer_sender.rs:108-167`) with no check against
the `receiver_address` passed to `create_receive`, and `create_lightning_invoice`
(`clients/libs/rust-sdk/src/ssp.rs:1123-1130`) hands the invoice to the payer without ever calling
`peek_pending_transfers` to confirm a transfer addressed to its own auth key exists. So the trustless-
RECEIVE claim needs three fixes, not one.

**(3) SGX-lane divergence — confirmed live and running in BOTH directions.** Every SE-behaviour finding
above was grepped across both trees; the results:
- C-3 (no auth) and C-13 (session magic) hold in **both**, and C-13 is *worse* on the SGX lane (enclave
  abort → `SGX_ERROR_ENCLAVE_CRASHED` until reload and re-provisioning).
- C-5 is SGX-only, and it nullifies the SGX trust claim entirely.
- C-4 is lockbox-only — **but `docker-compose-main.yml:32` pulls `mercurylayer/lockbox:latest`, so the
  one mainnet compose in the repo ships the untrusted lane.** The divergence here runs the opposite way
  from the historical pattern: the *deployment* is on the dev lane.
- The census's "enclave-authoritative" signature count is **not enclave-authoritative in either tree**:
  `sig_count` is a plain `INTEGER DEFAULT 0` column (`enclave/App/database/db_manager.cpp:89`)
  incremented and read entirely by the UNTRUSTED App (`:369-379`, `:474`, `:489-511`), and
  `grep -rn "sig_count" enclave/Enclave/` returns **nothing** — the trusted enclave never sees, signs or
  attests it. Any operator forges the receiver census with one UPDATE. This is a premise of the whole
  anti-hidden-state design and it does not hold. **Treat this as a blocking design item alongside §2.**

**(4) Audit [15] auth-nonce griefing — still DoS-only, but its blast radius grew.** The replayable
`signed_statechain_id` is the entry ticket for C-13's process abort, which is now a whole-network
outage plus third-party census poisoning rather than a per-coin nuisance. Fix the magic check
(cheap) and it reverts to DoS-only; a nonce is still the right long-term fix.

## 5. What was checked and found sound

This section matters as much as §2. The following invariants were examined adversarially and **hold**:

- **Aggregate-key invariance across handover.** `key_update` computes `s' = s + t2 - x1` with the
  receiver absorbing the complement, so `s + o` is preserved (`lockbox/src/enclave.cpp:205-243`,
  `enclave/Enclave/Enclave.cpp:297-381`). Pre-signed exits stay valid across transfers, exactly as
  designed. (This is also what makes C-4 catastrophic — the property is correct, the key storage is not.)
- **The census EQUATION is right; only its inputs are unguarded.** `expected = flat_backups + tiers +
  superseded` (`tesr.rs:1500`) with exact equality genuinely does catch a hidden co-signed state — the
  three critical bypasses (C-1 unbound authority, C-2 duplicate counting, C-3 remotely bumpable counter)
  are all attacks on the *inputs*, not the arithmetic. The design is sound; the plumbing is not.
- **The flat-backup term is properly guarded.** INV-5 `ladder_decrements_by_interval`
  (`lib/src/transfer/receiver.rs:329-335`) rejects duplicate `tx1`s, and `sdk55_backup_chain_adversarial.rs`
  proves it. This is the model the superseded term should copy.
- **`verify_child_bundle` binds correctly.** `tesr.rs:1583-1604` derives `A_parent` from the on-chain
  `F.spk` and cross-checks the server-recorded aggregate — the exact pattern C-1 needs. The child lane
  also correctly binds `st_out0.value` to the declared `out_value` (`:1807-1821`), which is the pattern
  H-1 needs. Both fixes have working precedent in the same file.
- **`validate_tx0_output_pubkey`** (`lib/src/transfer/receiver.rs:189-212`) genuinely proves the funding
  output is the enclave key combined with the receiver's key — it is already called at
  `transfer_receiver.rs:683` and is the correct anchor for C-1's fix.
- **The receive path is atomic on the v4 lane.** `transfer_receiver.rs:882-932` completes the key
  handover BEFORE `persist_child`, and the ordering comment is accurate for v4. (The v3 legacy branch
  is the exception — see C-14.)
- **`watch_pass` is correctly reactive.** Gating on `outpoint_spent(F)` (`tesr.rs:1114-1119`) is what
  makes per-block polling safe and preserves the "idle coins never age" property. The design is right;
  the missing piece is a child analogue (C-10).
- **`unilateral_exit` and both `auto_exit_due` loops correctly filter `CoinStatus::CONFIRMED`**
  (`wallet.rs:702`, `:732`, `:1059-1064`), and the comment at `:1060-1066` names the exact
  accidental-loss hazard. The guard is right; `defend_ladders` is the one place it is missing (C-11).
- **`export_watch_bundle` correctly refuses to emit an allocation-destroying sweep for carriers**
  (`watchtower.rs:98-104`). That `(None, None)` is deliberate hardening, not a bug.
- **`split_coin`'s [B1] refusal is correct** for the shape it checks (`transfer.rs:698-705`) — the
  defect is that three colored sites and `ensure_exact_coin` never got the same check (H-4, H-7).
- **The uncommitted `transfer_many` SEED fix is directionally correct.** `transfer_many` now dispatches
  on shape and routes a laddered parent into `ManyRoute::InLadderRoot` (`transfer.rs:448-497`), which is
  the right answer to the reported bug — it no longer builds a plain split of a laddered coin's `F`.
  **But it is not safe to land yet**: routing more traffic into the in-ladder lane amplifies C-2, C-10,
  C-11, H-2 and H-3 (H-3 in particular makes the *default* batch payment unclaimable whenever the parent
  was itself received). `sdk69_transfer_many_inladder.rs` splits a self-deposited parent, so it cannot
  catch H-3. Do not ship the fix without at minimum H-3 and C-10.
- **`is_batch_expired` and `validate_batch`'s move onto the latch clock** (audit [2]/H4,
  `server/src/endpoints/transfer_receiver.rs:189-205`) are correct in themselves; C-7 is that the
  *sender* half was never moved with them.
- **`/transfer/transfer_preimage`'s use of the same self-signed validator is NOT vulnerable**
  (`server/src/endpoints/lightning_latch.rs:118-126`) — there the supplied key is subsequently the DB
  lookup key, so it is bound to stored state. Only `/transfer/unlock` is broken.
- **`GET /transfer/batch_statechains/<batch_id>` does not leak plain-batch membership**
  (`server/src/database/lightning_latch.rs:166-170` reads only the `lightning_latch` table), and
  `/info/keylist` does not emit statechain_ids in `PubKeyInfo` (`server/src/endpoints/utils.rs:139-196`).
  Two claims that circulated during review are wrong; the realistic attacker for C-6's atomicity break
  is a batch participant.
- **`PARENT_V2_BASELINE`'s error direction is safe.** It only ever under-counts, so H-3 is fail-closed
  and can never absorb hidden state.
- **`CHILD_V2_BASELINE = 0` is arithmetically exact at any hop depth** — `child_retransfer`
  (`tesr.rs:813-831`) and `child_in_ladder_split` each add exactly one co-sign per superseded entry and
  never add a flat backup, so the child lane's own baseline is correct. Only the *parent* baseline is
  wrong.
- **The `sign/first` advisory lock** (`server/src/database/sign.rs:11-21`) is the correct pattern; H-6
  is that `/transfer/receiver` never got it.
- **`network` is bound end-to-end** through `require_network` against the receiver's own backup address
  (`tesr.rs:1361-1370`, `:1575`) — which is why H-2's fix costs nothing.
- **`docker-compose-hw.yml`'s `enclave-sgx` service declares no published ports** and is
  container-network-only. Operators following that file avoid C-3's host exposure (though not
  container-to-container reachability).
- **No refuted-but-real theft was found in the RGB consignment arithmetic itself.**
  `validate_offchain_chain_info` + `accept_offchain_amount` correctly validate the consignment; C-9 is
  that the SSP runs *only* that and skips the Bitcoin-layer half.

## 7. Remediation order

**Tier 0 — deployment, before anything else (hours).** Nothing below matters until these are done,
because they make every other guarantee vacuous.

1. Rotate the SE seed and Vault token; purge all four literals from the tree and git history; remove
   published `18080`/`5432`/`5433`/`8200` port bindings from every compose; refuse to boot with a

2. Add authentication (mTLS or shared secret) on every SE route in **both** trees. **(C-3.)**
3. Add the 4-byte MuSig session magic check in the coordinator and both SE trees. **(C-13; one line,
   prevents a one-request total outage.)**
4. Rebuild the enclave via `HW_RELEASE` with an offline key, `<DisableDebug>1</DisableDebug>`, non-zero

5. Decide and fix the mainnet lane: `docker-compose-main.yml` currently ships the lockbox image with

bug, but landing it before H-3 and C-10 converts a known theft path into a default-path unclaimable
payment plus an unwatched child for every batch recipient. Land it in the same change as items 17 and 20.
