# Mainnet audit remediation (NOT_READY)

NOT READY for mainnet. No CONFIRMED unconditional theft primitive survived (the deployed lockbox/src enclave DOES have the C1 atomic load-and-consume secnonce guard at db_manager.cpp:294-297, which caps signatures per secnonce and prevents nonce-reuse key extraction). But there is no CRITICAL. However, multiple CONFIRMED HIGH fund-loss/theft-under-realistic-conditions paths remain open, and per the rubric any CONFIRMED HIGH fund-loss/theft path forces NOT_READY. The most serious clusters: (1) the SE single-use/budget/epoch fork-prevention guards fail OPEN on any DB error, and the enclave does NOT enforce those invariants, so a load-induced race yields two SE co-signatures over conflicting spends of one terminal node -> off-chain fork/double-spend; (2) the H4 Lightning-latch batch-timeout remediation was NEVER landed (validate_batch still keys on the 120s batch_timeout, ignoring the 25h latch expires_at), so honest SSPs lose the Lightning payment on any settlement slower than 120s and a malicious receiver can make the SSP keep both the coin and the money; (3) the SSP pre-payment value gate is bypassable on BOTH the SATS leg (peek trusts an un-validated, value-inflatable branch amount) and the RGB leg (RGB invoices skip the value gate entirely) -> unbounded SSP drain per swap; (4) three separate token-carrier BTC-spend paths (start_lightning_swap, withdraw/unilateral_exit, and bundle-only restore) silently destroy RGB-USDT allocations; (5) received USDT booking is non-retriable and strands funds on a transient error; (6) split funding outputs have no dust floor, stranding sub-coins with no broadcastable exit; (7) the watchtower exit_deadline_block is computed with wrong (systematically too-late) arithmetic, causing offline-clawback theft for integrators honoring the documented contract; and (8) validate_branch does not enforce INV-4 branch-locktime, letting a malicious sender ship an unbroadcastable future-locktimed branch and claw the coin back. OPERATIONAL CAVEAT: the C1 nonce fix lives in the lockbox/src build (db_manager.cpp) that is the wired mainnet service; the separate enclave/App SGX implementation lacks the equivalent atomic consume, so the SGX lockbox MUST be rebuilt and redeployed before any SGX-backed deployment inherits the C1 protection — until then an SGX deployment is exposed to the nonce-reuse key-extraction path. Fix the HIGH items, land H4, and confirm the deployed lockbox binary carries the atomic consume before mainnet.

### [1] HIGH server/src/database/deposit.rs:147  (new=True prior=)
**SE single-use/budget/epoch fork-prevention guards fail OPEN on any DB error; enclave does not enforce them -> two co-signatures over conflicting spends of one terminal node -> off-chain fork/double-spend**

Yields an off-chain double-spend of custodied funds. Race-dependent, so HIGH not CRITICAL.

## External review response (2026-07, reviewer commit `65f9377`)

An independent reviewer filed 5 findings against `65f9377` + the RGB fork. All 5 verified against
current HEAD (adversarial workflow + cross-check) and addressed:

- **F1 (HIGH) unauthenticated `/transfer/unlock` — FIXED + tested.** The guard only rejected when
  `auth_pub_key` was *present* and invalid, so a bad `auth_sig` with a NULL `auth_pub_key` cleared
  the receiver-side `locked` bit with no valid signature, and an unknown statechain_id panicked the
  handler (`fetch_one().unwrap()` → 500). Now: accept ONLY if the current-owner sig validates OR an
  `auth_pub_key` is supplied AND validates under it; `update_unlock_transfer` returns a typed
  not-found. The two honest callers (LN-latch owner-unlock with null key + valid owner sig; receiver
  unlock with its new key) are unaffected. NOT tightened to match the supplied key against the DB —
  the receiver's key isn't registered at unlock time, so that would break the legitimate path.
  Regression: `sdk12` Part D (bad-sig + null key → 403 for both real and unknown ids).
- **F2 (HIGH) sign/second consumed the spend budget on lockbox failure — FIXED.** The challenge was
  bound before the lockbox call (required — it is the MuSig2 nonce-reuse guard) but `challenge IS
  NOT NULL` was also the only "finalized" signal, so a transient lockbox fault burned the owner's
  budget with no usable signature. Split the states: migration `0008` adds `partial_sig_issued`
  (conservative backfill from `challenge IS NOT NULL`), written only after a valid partial sig is
  parsed (fail-CLOSED on the marker write — under-counting is the INV-19-fork-dangerous direction);
  `count_finalized_signatures` now counts it. Nonce-reuse protection untouched (`sdk12` Part C green).
- **F4 (MED) derived-token fallback silently spent paid onboarding tokens — FIXED.** `get_derived_tokens`
  now returns `Ok(None)` ONLY when the SE doesn't offer the endpoint (404/403), so `take_derived_tokens`
  falls back to onboarding tokens ONLY then; a transient/refused/exhausted error is surfaced, never
  silently paid. `sdk36` green.
- **F5 (MED) token claim reported success while RGB acceptance failed — FIXED.** A coin that received
  a consignment but failed to book was absent from `token_carrier_outpoints` (booked-only), so plain-BTC
  selection — including `auto_refresh_due`, which would re-anchor and DESTROY the allocation — could
  spend it. Added `consignment_bearing_outpoints` (pending carriers) + `unspendable_as_btc_outpoints`
  (booked ∪ pending), used by every plain-BTC guard; `ClaimResult.token_results` exposes per-coin
  Booked/Pending/Rejected. A PERMANENTLY-invalid consignment (griefer's garbage) is un-quarantined via
  a `token-rejected-<id>` marker so it can't lock a victim's sats forever. `sdk29` token claim/book/
  settle green.
- **F3 (HIGH reliability) split/combine commit ordering — DOCUMENTED (TRUST-MODEL B10).** Real, but the
  reviewer's proposed nonce-replay recovery is *unsound* (the enclave nulls the secnonce on first sign,
  so a replayed sign/second never returns the original server partial sig) and no safe reordering exists
  (budget must precede the co-signature for INV-19). Unilateral exit is the value backstop; a durable
  prepare/commit (persist the assembled signed tx, replay locally) is the real fix — deliberately not
  shipped as a half-mechanism (a persist with no tested recovery reader is false comfort).
